### 诉求 1：图片/视频直接在消息页打开，只有「其它文件」才跳文件页

改动落在**一处判断**上：`msgImagePath` → `msgMediaPath`，判据从 `isImageName` 放宽到
`isMediaName`（图片 **或** 视频）。返回空串的语义就是「这一类点了跳文件页」。

| 类型 | 气泡里显示 | 点一下 | 长按 |
|---|---|---|---|
| 图片 | 128×128 缩略图 | 全屏预览（捏合/双击/拖动） | 存相册 |
| **视频** | 128×128 **首帧** + ▶ 角标 | **全屏播放器**（内置 `Video`，带进度条） | 存相册 |
| 其它（zip/apk/pdf…） | 只有文件名 | 跳「文件」页 | — |

**视频缩略图是本轮唯一的硬骨头**：把视频路径直接喂给 `Image` 只会得到**一块空白**
（图/视频的解码器根本不是一个）。

正解是 `media.createAVImageGenerator()`：

```ts
f = fileIo.openSync(path, fileIo.OpenMode.READ_ONLY);   // fd 要活到 fetch 返回
gen = await media.createAVImageGenerator();
gen.fdSrc = { fd: f.fd } as media.AVFileDescriptor;
const pm = await gen.fetchFrameByTime(
  0, media.AVImageQueryOptions.AV_IMAGE_QUERY_CLOSEST_SYNC, { width: 192, height: 192 });
await gen.release();
```

三个必守点：**fd 必须活到 `fetchFrameByTime` 返回**（提前 close 直接解不出来）；
**`release()` 是 Promise，要 await**；**取「离 0 最近的关键帧」而不是第 0 帧**
（不少视频开头是纯黑，关键帧才有画面）。

**异步结果的可见性坑**：`videoThumbs` 是普通 `Map`，ArkUI 观察不到 `Map.set()`。
所以配了一个 `@State videoThumbTick` 计数器，每解出一张 +1；并且**消息页 / 文件页两个
`ForEach` 的 key 都要带上 tick** —— key 不变的话 ForEach 会复用旧行，缩略图永远不出现。
（`List` 是懒加载的，只重建可见那几行，代价可忽略。）

另一条纪律：解码**不在 `@Builder` 里触发**（`@Builder` 每次重绘都会重新执行，
在里面起异步任务等于每次重绘提交一次）。统一放在 `refreshReceived()` 末尾预热，
渲染保持纯粹。

### 诉求 1：消息页也要显示图片缩略图

**做法**：`chatBubble` 里那段「文件气泡」抽成独立的 `@Builder chatFileBubble(m, imgPath)`，
收到的图片消息先渲染 **128×128** 缩略图（同样配 `sourceSize({192,192})` 压解码尺寸 ——
聊天记录上限 200 条，不压的话每张原图都会整张解进内存）。

**⚠️ 本轮最容易踩的坑：消息里只有文件名，路径从哪来？**

消息表 `ChatMessage` 只存了 `content` = **对端发来的原名**。所以 `refreshReceived()` 时顺手建一张
`文件名 → 沙箱路径` 的表（`rebuildRecvIndex`）。**但只登记真名是不够的**：

> 对端发来的图叫 `photo.jpg`；沙箱里已经有一张同名图时，落盘名会被
> `FileKinds.dedupeName` 改成 **`photo(1).jpg`** —— 而气泡里存的永远是**原名** `photo.jpg`。
> 只登记真名的话，**第二张同名的图永远没有缩略图**。
> 而 `IMG_0001.jpg` 这种一发就是一批，重名是常态。

所以每个文件登记**两个键**：真名 + 去掉重名后缀的别名（`stripDedupeSuffix`：
`photo(1).jpg` → `photo.jpg`，只认「数字包在圆括号里」这一种形态）。
`list` 是按时间倒序的，所以「先到先得」= 取最新那张，符合直觉。

### 诉求 1：删除确认弹窗的「文件名」字体过大 → 显示不全

**根因**：用的是系统 `showDialog`，文件名被拼进了 **title** 里（`删除「<文件名>」？`）。
系统对话框的 title 字号是内部固定的（比正文大一档），**且不按内容折行** ——
文件名一长必然被截，用户看着一个残缺的名字确认删除。

**修复：整条弹窗改成自绘**（`Stack` + `@State` 浮层，与二维码弹窗同一套路）。
调用点写法**完全不变**（仍是 `await this.confirmDialog(...)`，内部靠存 `resolve` 兑现）：

| 部位 | 处理 |
|---|---|
| 标题 | **固定短文案**（「删除文件」/「清空接收到的文件」），16fp —— 标题不承载可变内容 |
| **文件名** | **单列一块 13fp 小字**（比标题小一档）+ `wordBreak(BREAK_ALL)` + `maxLines(5)` |
| 风险提示 | 12fp 灰色一句话（「删除后无法恢复」） |
| 按钮 | 取消 / 删除（红字浅底，与危险操作同色） |
| 遮罩点击 | = **取消**（危险操作默认落在安全侧） |

13fp × 5 行 ≈ 110 个字符，正常文件名不可能再被截；无空格的长英文名 / 哈希名也能折行。

**顺带修好的两处**：① 返回键现在能关这个弹窗了（自绘浮层框架管不着，必须在 `onBackPress` 里补分支）；
② 点卡片空白处不会冒泡到遮罩误触取消（卡片自身挂了个空 `onClick`）。

**验收**：点「删除」→ 弹窗里**完整看到文件名**（长名自动折行）；点「取消」不删。

### 诉求 2：接收到的图片要缩略图 + 点了能看大图

**① 列表缩略图**（48×48，只给图片类文件，按扩展名识别）

- 沙箱 URI **必须**用 `fileUri.getUriFromPath(path)` 取（规范形态 `file://<bundleName>/<绝对路径>`）。
  **手拼 `'file://' + path` 不行** —— `Image` 认不出来，症状是缩略图**恒定空白且不报错**。
- ⚠️ **必须配 `sourceSize({width:96, height:96})`**：不压解码尺寸的话，40 张 1200 万像素的
  原图会被**整张**解进内存，列表一滚就是几百 MB。这是本轮唯一的性能红线。
- 缩略图下层垫了一个「图片」占位文案：解码完成前 / 失败时显示，不留空洞。
- 顺带把右边的「元信息行」钉成 `maxLines(1)` —— 左边多了 48vp 之后，窄屏上这行
  要是允许折行会把卡片撑高。

**② 点击看大图**：**普通态点一下行**进全屏预览（多选态仍然是勾选，优先级不变）

| 手势 | 行为 |
|---|---|
| 双指捏合 | 1x ~ 8x 缩放 |
| 单指拖动 | **只在放大后**生效 |
| 双击 | >1x 复位 / =1x 放大到 2.5x |
| 「关闭」按钮 / **系统返回键** | 退出预览并复位 |

> 刻意**不做**「单击任意处关闭」：放大状态下单击太容易误触，而双击复位本身就会吃掉单击。

**验收**：收到图片 → 列表里看到缩略图；点一下 → 全屏；双指放大 / 拖动 / 双击复位；

### 诉求 4：对方关掉 App，十秒左右才显示下线（本轮重点）

**根因：上一版的判死模型有一个从未成立的隐含前提。**

```
单播探活发出 → 对端回包 → RTT ≤ 500ms → 信任分 +1 → 攒够 3 次才允许"快速判死"
```

这条链要求**对端应答我们的 `UDP_GET_DEVICES`**。真机上对端（1.35 平板）**不理它** ——
它只按自己的周期广播心跳。于是：

- RTT 判据永远命不中（偶尔命中的那次也只是**撞上它自己的周期广播**，间隔往往 > 500ms）；
- 信任分**从未攒够 3 次** → 「快速判死」形同虚设 → 一直走 `DEVICE_OFFLINE_MS` = 8s 兜底；
- 加上 1s 巡检粒度与用户计时误差，看到的就是「十秒左右」。

**修复：换成 TCP 连接复核 —— 一个不依赖对端应用层行为的确定性事实。**

| 连接结果 | 含义 |
|---|---|
| 成功 | 设备活着（服务在监听 5856） |
| 立即 RST | 主机活着但服务已停 → 对我们等同于下线 |
| SYN 超时 / 不可达 | 设备不在 / 已关机 / 不在同网段 |

**四个关键细节**

1. **只建连、不发任何字节**就关闭。发魔数会被对端的分流逻辑引到「私有协议」分支上，
   等于凭空给对方造一条半截握手；什么都不发，对端读到 EOF 自行收尾。
2. **安全阀**：只有**曾经 TCP 复核成功过**的设备才允许用「复核失败」判死
   （`DEVICE_TCP_VERIFY_MAX_MISS = 3` 次验证机会）。
   否则万一某台设备的文件端口本来就不可连（防火墙 / 未开共享 / 端口被改），
   我们会在它明明在线时反复判死 → 列表**持续闪烁**，比慢更糟。
3. **连续 2 次失败**才判死（`DEVICE_TCP_PROBE_MISS_LIMIT = 2`），抗单次网络抖动；
   任何一次成功、或收到它任意一个 UDP 包，失败计数立即清零。
4. `DEVICE_OFFLINE_MS` = 8s 的**兜底保留**（只对「TCP 也验证不通」的设备生效）。

**新时间线**（对端关掉 App 后）

| 时刻 | 动作 |
|---|---|
| t = 0 | 最后一次收到它的心跳 |
| t ≈ 1.2s | 安静超过 `DEVICE_PROBE_QUIET_MS(1200)` → 发 UDP 单播探活 + **TCP 复核 #1** |
| t ≈ 1.2s | Android 端口已关 → 立刻回 RST → 复核失败 → miss = 1 |
| t ≈ 2.2s | 冷却（`DEVICE_TCP_PROBE_COOLDOWN_MS` = 700ms）已过 → **TCP 复核 #2** → 失败 → miss = 2 → **判死并立即移除** |

预期 **2~3s** 从列表消失（上一版 ~10s）。

**验收**

| # | 场景 | 期望 |
|---|---|---|
| ① | 对方**正常退出 / 关共享** | 本机列表 2~3s 内消失（对端发 `1003` 时立即消失） |
| ② | 对方**强杀 App**（不发 1003） | 2~3s 内消失 |
| ③ | 对方**保持在线** | 列表**不得**闪烁 ← **本轮最需要盯的回归点** |

> ⚠️ 若某台设备出现「消失 2s 又回来、来回闪」，说明它的 5856 连不上
> （被防火墙拦 / 共享没开）。请把日志页里那台设备的 `TCP 复核失败 n/2` 一行发我，
> 我据此决定是否给它加豁免。

### 本轮踩坑（给以后的 AI / 自己）

**补丁脚本的行号区间必须完整包住整个语法块，并且要有校验。**

第一次构建直接失败在 `LanService.ets`：

```
ERROR 10505001: Duplicate identifier 'deviceInfo'   (LanService.ets:27 / :28)
ERROR 10505001: Cannot find namespace 'common'
ERROR 10505001: Cannot find name 'fileIo'
```

原因是补丁把 import 区间写成 `(25, 27)`，而真正的区段是 **25~28 四行**
（`common` / `fileIo` / `BusinessError` / `deviceInfo`）—— 少覆盖一行，
于是 `common`、`fileIo` 被整段删掉，而第 28 行的 `deviceInfo` 留了下来 → 重复声明。

已加的两道保险（见 `patch_v5015.py`）：

| 保险 | 作用 | 这次为什么没拦住 |
|---|---|---|
| `expect` 关键字校验 | 区间内必须出现指定串，防行号偏移 | 行号没偏移，是**区间本身划小了** |
| 括号增量一致（`{` − `}`） | 防「少写收尾大括号」 | `import { X } from` 的括号成对，增量相同 → 看不出少了整行 |

**教训**：区间边界不能靠"看起来差不多"，要从**语法块的起止**推 ——
`import` 区就是「从第一个 import 到最后一个 import」，不是「到第三个 import 为止」。
（同一脚本里 `dropDevice` 那次事故是同一种错：区间包住了整个方法，
替换块却只写到方法前半段。）

### 问题 1：首页的网址显示不全了（回归）

**根因（上一版自己引入的）**：5.0.13 给访问地址卡片加了「二维码」按钮，
于是「复制 / 二维码」两个按钮和网址挤在**同一行**，网址用 `layoutWeight(1)`
只能拿到「剩余宽度」—— 360vp 屏上两个按钮吃掉约 **130vp**，
留给 `http://192.168.10.146:5856` 这种 26 字符地址的只剩 ~200vp → 被省略号截断。

**修复**：按钮上移到标题行（标签 + 本机名 + 复制 + 二维码），
**网址自己独占一行铺满整宽**。可用宽度从 ~200vp 提到约 **332vp**，任何常规地址都放得下。

> 这与「文件页文件名被按钮挤扁」是**同一类错误**：凡是**用户数据**（网址 / 文件名 /
> 设备名）都不能和按钮抢同一行 —— `layoutWeight(1)` 只保证「占满剩余」，
> 不保证「够用」。心算：剩余宽度 = 屏宽 − padding − Σ固定宽子组件 − Σ间距。

### 问题 2：检测设备下线的速度还是不够快

**三层原因，第 1 层是真正的缺口：**

**(a) 收到「下线通知」包，我们根本不处理**（本轮最大发现）

协议里有一条 `UDP_DEVICES_OFF_LINE = 1003`：对端**正常关共享 / 退应用**时会广播它。
原版 Android 收到就直接删设备：

```java
// smali: com/fgsqw/lanshare/service/LANService.smali:14116-14157
const/16 v7, 0x3eb              // 1003
if (v3 == v7) {
    if (device.isCanRemove()) {
        devices.remove(key);    // ← 立刻移除，不等超时
    }
}
```

而本工程**只实现了发送**（`LanDiscovery.announceOffline`），**从没处理过收到的 1003**
—— 于是对方哪怕规规矩矩地告别了，我们也只能干等超时。
**修复：`onDeviceFound` 里补上 `frame.cmd === LCmd.UDP_DEVICES_OFF_LINE` 分支，走 `dropDevice()` 立即移除。**

**(b) 「被动等心跳」这个模型本身到顶了**

「多久没心跳就判离线」有一条绕不开的下界：**必须大于对端的心跳周期**。
官方版心跳 5s ⇒ 纯超时最快只能做到 7~8s，再往下调就会「丢一个包→误判离线→下一轮又冒出来」来回闪。
这就是上一版把 15s 调到 9s 之后用户仍觉得慢的根本原因 —— **不是参数没调到位，是模型到顶了**。

**修复：换成主动问。** 设备安静超过 `DEVICE_PROBE_QUIET_MS`(2s) 就给它发一个
**单播** `UDP_GET_DEVICES`（对端对这个报文的处理就是立刻单播回心跳，天然就是一次 ping）：

- 活着 → 毫秒级回包，`lastSeenMs` 刷新 → 永远不会误判；
- 已关 → 没人应答，超过 `DEVICE_PROBE_DEADLINE_MS`(2.5s) 即判死。

⚠️ 安全阀（重要）：我们**分不清**收到的包是「对探活的应答」还是「对端自己的周期广播」
（两者都是 `UDP_SET_DEVICES`）。若不区分，一个「只广播、从不理探活」的设备会被误判。
所以用 **RTT ≤ 500ms** 做近似判别，并要求**连续 3 次**命中才对该设备启用快速判死
（误判概率 ≈ 0.1³）。没攒够凭据的设备继续走 8s 兜底。

**(c) 顺带把 `SCAN_TIME` 从 5s 调到 3s**（只加快我们自己的广播节奏，协议不变）。

**预期时间线**：对端正常下线 → **立刻**消失；对端被强杀/拔电 → **4~5s**；其余 → 8~9s 兜底。

### 问题 3：接收文件过程中界面还是卡顿，切一下 Tab 卡好几秒

> 「切 Tab 卡好几秒」是个很有信息量的现象：Tab 切换动画本身只有 300ms，
> 被拉成好几秒说明 **UI 线程被占满了，动画拿不到帧**。

**根因（两处叠加）：**

**(a) 10Hz 的进度刷新在触发「整页重建」**

进度是唯一高频变化的字段（约 10 次/秒），而它和其余字段共用 `this.snapshot`。
`emit()` 之后 UI 侧 `this.snapshot = s` —— 整页上几乎所有组件都在读 `this.snapshot`，
一次赋值等于**整页重建**（三个 tab 的 Builder + 设备列表 + 所有卡片全跑一遍）。

**修复**：进度拆成独立 `@State`（`tText` / `tPercent`），**不再赋值 `this.snapshot`**；
其余字段先用签名（`state|localIp|webUrl|…`）比较，**没变就不赋值**。
于是 10Hz 的进度刷新只重渲染那一个浮层，页面主体一动不动。

**(b) 接收循环里的同步逐字节解密把主线程按住**

`FileCrypto.decData` 是**逐字节 JS 循环**（同步），而单帧上限 `MAX_FRAME` = **8MB**
—— 整块解一次就能按住主线程上百毫秒；16 条连接并发时几乎排满。

**修复**：解密按 **512KB 切片**，并在累计超过 **16ms** 时 `setTimeout(0)` **让出一帧**
（`V5Transfer.yieldFrame`，与 `HttpRouter.yieldFrame` 同一手法）。
单次连续占用上限被压到「一片解密」的几毫秒，让出频率 ≤ 60 次/秒，吞吐损失可忽略。
⚠️ 让帧点必须在「累加 + 节流判断」**之后** —— 那两句之间插 await 会让 16 条连接的累加交错，进度条又开始乱跳。
v4 路径（`FileTransfer`）同样处理。

### 问题 4：多选后取消保存，不该退出多选

`batchSaveSelected` 里 `saveMany` 之后**无条件** `exitFileSelect()`，
于是用户勾了 N 个文件、点保存、又按了取消 → 勾选全被清掉，等于白勾一遍。

**修复**：`ExportService.saveMany` 改返回 `SaveOutcome`（`cancelled` / `saved` / `msg`），
UI 只有 `cancelled === false` 才收起多选；取消时**原样停在多选界面**，勾选全保留，可以再点一次。

> 只回一个字符串是不够的：UI 必须能区分「用户主动取消」与「保存失败」，两者后续处理完全不同。

### 问题 1：进度条仍不线性，到 70% 左右一下就跳到 100%

**两个叠加的根因（都在 v5 的 1110 分片接收路径）：**

**(a) 上报的节流状态是「每条连接私有」的 —— 一次百分比变化被上报 16 遍**

```ts
// ❌ 旧：tickAt / tickPct 是 receiveSegment 的局部变量，每条连接一份
let tickAt: number = 0;
let tickPct: number = -1;
...
if (pct !== tickPct || nowMs - tickAt >= 250) { ... }
```

16 条连接并发推进，各自的 `tickPct` 都停在旧值 —— 于是全局百分比从 N 变到 N+1 时，
**16 条连接会各自上报一次**。1GB 文件凭空产生 16×100 ≈ **1600 次上报**，其中 15/16 是重复值。

**(b) 每写一块都 `openSync` + `closeSync` —— 同步系统调用压在 UI 线程上**

`CHUNK = 1MB - 12`，1GB 文件 ≈ 1000 次 open/close。全部是**同步**调用且跑在 ArkTS
的单线程事件循环上 ⇒ 落盘被拖慢、界面被堵 ⇒ 进度显不出来、末段猛涨。

**修复：**

1. **上报节流状态搬到 `SegPart` 上共享**（`lastReportAt` / `lastReportPct`）；
   判断与写回之间无 `await`，单线程下天然原子，第一条通过的连接就把状态吃掉。
2. **每条连接独占一个 fd 全程复用**（`receiveSegment` 打开一次、片结束才关），
   写入改成 `fileIo.lseek(fd, pos)` + `await fileIo.write(fd, buf)`：
   - 每个 fd 有独立 filePointer，16 条连接各持一个 → 互不干扰；
   - 不用 `write(..., {offset})` 是因为 SDK 的 `offset` 语义是「**当前 filePointer** + offset」
     （`@ohos.file.fs.d.ts:5738-5748`），`write` 会推进 filePointer，复用 fd 时会**双重偏移**。
3. 进度条加 **240ms 线性过渡动画**：即使百分比偶尔一跳，视觉上是「追上去」。

### 问题 1：接收进度条「一直在 1% 和 2% 之间跳动，然后立马 100%」

**根因（只出现在 v5 的 1110 分片接收路径）**：上报的进度分子是 `part.received + got`，而

- `got` = **本片**已收字节（片内局部值）
- `part.received` = 已完成片的字节和，**只在「整片收满」时才 `+= len`**

16 片是**并发同时推进**的 ⇒ 每条连接上报的都是「自己那一片的局部进度」，互相覆盖，
数值就在低区间里来回跳；等 16 片几乎同时收满，`part.received` 一次性跳到 fileSize → 直接 100%。

> **佐证**：发送侧的 `SegSend.sent` 本来就是「每块累加、跨连接共享」的单调计数器
> —— 接收侧没跟它对齐，这才是差异所在。

**修复**：

1. `SegPart.received` 语义改为**每落地一块就 `+= flen`** 的跨连接共享计数器；
2. 上报的分子改用 `part.received`（不再 `+ got`）；
3. 片完成处**删掉** `part.received += len`（否则翻倍），只保留 idx 去重与片数累加；
4. 新增 `counts` 标记：该 idx 若已收齐过（重传）则不再重复累加。

**为什么这样就单调了**：任何一次上报的分子都是「全局已落地字节」，
与是哪条连接、哪一片上报无关 ⇒ 必然单调递增。

稍长一点就被省略号截断。

**修复**：改成 `Column` 两段式 —— 文件名**独占整行宽度**且 `maxLines(2)`，

### 修的是什么

**PC 一次发 ≥2 个文件，第 2 个起必然失败。**（单文件正常，所以之前一直没暴露）

V5 协议里，**发送端在每个文件的数据块之后都会补发一帧 12 字节结束帧**
（`head[0]=2 FS_END`、`arg=0`、`len=0`）：

| 端 | 取证 |
|---|---|
| PC `baseSend` | `0x1400223ad: cmpq 80(%rax),%r14 ; je 0x1400224c0`（已发满）→ `0x1400224c0: movl $2,%edx ; callq DataEnc::setByteCmd` → `send(data,len,0)`（未发满走 `$3` = FS_CLOSE） |
| 1.35 `LANService.D` | `dump_D.txt` 320-343：`setInt(v0,-1,0)` → `setInt(v0,0,4)` → `v0[0] = (发满 ? 2 : 3)` → `setInt(v0,0,8)` → `write(v0,0,12)` |
| 本机 `sendPlain` | 本来就发：`endFrame.setStreamCmd(LCmd.FS_END)` |

**而 PC 收端 `baseRecv` 就是靠这一帧判文件结束**：
`140022dd1: cmpb $1,%al ; jne 140022f48`（非数据帧）→ `140022f48: cmpb $2,%al ; je 140022f10`（FS_END → 退出，**不回 ack**）。

本机 `recvBody` 的循环是 `while (subTotal < item.length)` —— **收满即跳出，从不读这一帧** →
它留在 TCP 缓冲区 → 被**下一个文件的 recvBody** 当帧头读走 → `break` → `0 != item.length`
→ 回 `FS_BREAK(6)` → 整体失败。

### 改了什么

`V5Transfer.recvBody()` 在 `while` 循环**之外**补一段（收满后才执行）：

```ts
if (subTotal === item.length) {
  const tail = await chan.readExactly(12, END_FRAME_WAIT_MS);   // 5s
  if (tail !== null) {
    const tcmd = tail[0] & 0xFF;
    if (tcmd === LCmd.FS_END)      { /* 吃掉；len>0 也一并吃掉 */ }
    else if (tcmd === LCmd.FS_CLOSE) { /* 对端判失败，按已收字节落地 */ }
    else { return false; }          // 其它命令 = 帧流错位，明确报错
  }
  // tail === null（对端不发结束帧的旧实现）→ 回退到按字节数判结束
}
```

**顺序不能反**：循环内最后一块的块级 ack 已经回过，对端才会发这帧。
先等帧、后回 ack 就是双方对等死锁。

# 5.0.21 —— 修复「官方安卓发文字鸿蒙收不到 / 鸿蒙发文字安卓收到两次」

**用户报告**：官方安卓版发文字消息 → 鸿蒙版收不到；鸿蒙版发文字 → 安卓版**收到两次**。

## 根因 1：UDP 帧解析无条件读「已知设备表」（→ 官方安卓的文字一条都收不到）

UDP 帧 = 明文 MAGIC `0x66677371`(4B) + 整帧逐字节 `((b-1)&0xFF)^0x45` 混淆。
设备头固定 8 个字段（`port / ip / name / devMode / uuid / dataVersion / 77 / 2`），
**第 8 个字段之后 v4 与 v5 就分叉了**：

| 版本 | 8 字段之后 |
|---|---|
| **v4**（官方 `Config.DATA_VERSION = LVersion.DATA_VERSION_4`） | **直接就是命令专属参数**（`messageEnc` 密文 hex / 包名 / 剪贴板） |
| **v5**（1.35 修改版） | `int 已知设备数` → `N×(int port, String ip, String name)` → 命令参数 |

证据（官方 Java 源码，非推断）：
- `LANService.java:1917` `makeDataEncUdp()` 只写 8 个设备字段，**没有**已知设备表。
- `handleUdp()` 读完 8 字段后直接 `dec.readUTF()` 取命令参数。

旧 `V5Udp.parse` **无条件** `dec.int()` 当设备数 → 把 v4 的 `messageEnc` 长度前缀
（实测 181）当成设备数 → `readKnown` 把整段消息吃穿 → `extras` 全空 →
收到 `1004` 时打 `UDP 消息帧缺少密文字段` → **消息被丢弃**。
（设备发现不受影响，因为发现只读 8 字段 —— 症状就是「能看到设备、收不到文字」。）

**修复**：按对端广播的 `dataVersion`（= uuid 后缀，`V5Header.read` 已解析并剥掉）分流：

```ts
frame.device = dev;
if (dev.dataVersion >= LanConfig.V5_MIN_DATA_VERSION) {
  const knownCount: number = dec.int();
  frame.known = V5Header.readKnown(dec, Math.min(knownCount, 64));
}
```

I .../LanService: UDP 消息帧缺少密文字段，来自 192.168.10.186
```

## 根因 2：设备表 key 用 uuid、存活续命用 IP（→ 安卓收到两次）

`devices` 的 key 是 `uniqueUuid`，而 `tcpProbeStep` 的 TCP 复核**只认 IP** ——
复核成功就把 `d.lastSeenMs` 刷新。于是同一台物理机只要换过 uuid
（重装 App / 官方版与 1.35 双版本共存 / 清数据），**旧条目会被新条目的存活续命**，
`DEVICE_OFFLINE_MS`(8s) 永远清不掉。

`onlineDeviceList()` 返回多条同 IP 记录 → 群发时**同一台设备收到 N 份**。

**修复前真机 hilog（同一秒三条，来自同一台 DBY-W09 @ 192.168.10.100）**：
```

**修复（两道保险）**：
1. `dropSameIpExcept(ip, keepKey)` —— UDP 发现（`:901`）与 `trackPeer` 入站（`:2378`）
   两个写入点都先清掉同 IP 的旧条目。**不清 per-IP 探测状态**
   （`probeSentAt / tcpEverOk / tcpProbeMiss / lastTcpProbeAt` 键是 IP，继续有效）。
2. `onlineDeviceList()` 兜底护栏 —— 即使残留多条同 IP 也只会各投一份，
   保留 `lastSeenMs` 最新的那条。

# 5.0.23 —— 修复「车机版安卓 1.35 收大文件卡在 ~99% 后失败」

**用户报告**（2026-10-01 18:18）：手机（鸿蒙）→ 车机（安卓 1.35，DiLink3.0 For BYD AUTO）发
`launchermap_3.9.151-20260930.apk`，进度到 ~99% 卡住，然后失败。

## 日志证据（实锤，18:37 那次重跑，手机=5.0.22）

```
10-01 18:37:07.257 v5 分片发送开始 launchermap_3.9.151-20260930.apk size=677501607 segs=16 segId=...
10-01 18:37:56.127 v5 分片[1/16] 30s 内未收到终态应答（已跳过 41 个 流控字节）
...（16 片全部同款：30s 内未收到终态应答，已跳过 41 个流控字节）
10-01 18:37:56.941 v5 分片发送失败 launchermap...：成功 0/16 片
```

**关键判读**：`已跳过 41 个 流控字节` = 发送侧在等终态时读到了 **41 个 `FS_NEXT(=5)`**——
而 `5` 既是**块级 ack**（每 2MB 一块回 1 字节）也是片级收尾的首字节。
说明**车机确实在收分片数据、并逐块回 ack** —— 它**支持 1110 分片接收**，并非"不支持分片"。
真正缺的是**每片结束的终态码 `2`(RECV_OK)**：30s 内 16 片**没有一片**读到终态 → 全部超时。

## 根因（修正措辞）：每片终态握手与本机不匹配，而非"车机不支持分片"

| # | 事实 | 证据 / 推导 |
|---|---|---|
| 1 | 发送侧对 **≥128MB 的普通文件** 走 `1110` 16 分片并发通道 | `V5Transfer.segEligible`：`size >= 128MB` 且非图片/视频（`SEG_MIN_SIZE = 134217728`）；`launchermap` 677MB ⇒ 被分片 |
| 2 | 车机**在收分片数据**（块级 ack `5` 在回），但**每片结束的终态码 `2` 始终不来** | hilog `已跳过 41 个 流控字节`（=读到 41 个 `5`）+ 16 片全 `30s 未收到终态应答` |
| 3 | 本机发送侧**按「每片」等一个终态码(2/3)**（`sendOneSegment` 709–753：循环读、遇 `5` 跳过、遇 2/3 收尾）；本机接收侧也**按片**回终态 `5+2`（`receiveSegment` 1172–1179），故「1.35→手机」「手机→手机」分片均成功 | 代码事实 |
| 4 | 车机安卓 1.35 接收端的终态语义**与本机不同**：最可能是**按整文件收满（所有 16 片到齐、received==fileSize）才回终态**，而非按片回。于是本机每片独立连接、片发完就在该连接上等终态 → 车机还差 15 片没到、不回这条连接的终态 → 30s 超时。日志「数据在收(41个ack)却等不到终态」完美吻合 | 由 #2 + #3 推得（无车机 1.35 接收源码，非 100% 确认，但现象唯一自洽解释） |
| 5 | `1101` 单连接通道对 1.35 **已实机验证可用** | `sendPlain` 整文件一条流：发完 → 收方收满 → 回终态 → 成功，天然绕开并行终态握手 |

**结论**：旧 UI 文案「对端可能不支持分片传输」是**误报** —— 车机并非不支持分片，而是
**分片(每片)结束的终态握手语义不匹配**。最稳修法是**分片失败自动回退 1101 单连接重传**：
保留两手机互传的 1110 加速，大文件发给任何 v5 对端都必成。

## 修复（`entry/src/main/ets/service/V5Transfer.ets` + `AppScope/app.json5`）

1. `send()`：**分片失败的文件并入 `plainFiles`，统一走 `sendPlain` 回退重传**。

   ```ts
   let segFailed: OutgoingFile[] = [];
   if (segFiles.length > 0) {
     // sendSegBatch 返回**分片失败的文件**（空数组 = 全部成功）
     segFailed = await V5Transfer.sendSegBatch(self, target, segFiles, onReport);
   }
   const retryFiles: OutgoingFile[] = plainFiles.concat(segFailed);
   if (retryFiles.length > 0) {
     if (segFailed.length > 0) {
       Log.w(TAG, `v5 分片失败 ${segFailed.length} 个，自动回退到 1101 单连接重传`);
     }
     const okPlain = await V5Transfer.sendPlain(self, target, retryFiles, encData, onReport);
     if (!okPlain) okAll = false;
   }
   ```

2. `sendSegBatch()`：**返回类型 `boolean → OutgoingFile[]`**（返回分片失败的文件列表），
   由调用方决定是否回退；全部成功时才报「已发送（分片并发）」。

3. `sendSegFile()`：**不再在此下「发送失败」定论**——只留一条 `Log.w`
   （「分片发送失败 …（将回退 1101）」），最终成败交给 1101 回退路径报。

4. `AppScope/app.json5`：`versionCode 5000022 → 5000023`、`versionName 5.0.22 → 5.0.23`。

> 回退走 `sendPlain` 时沿用调用方传入的 `encData`（固定 `false`），与 1101 既有通道完全一致。

# 5.0.25 —— 1110 分片「对端 1.35 报接收失败」真根因：缺片级 FS_END 结束帧

> 5.0.24 把本机判定改成「块全 ack 即成功」后，本机日志全绿（16/16 兼容模式完成），
> 但 **vivi 实测：对端 1.35 仍显示接收失败** —— 证明问题不在本机判定，而在**发送流本身**。

## 现象（5.0.24，19:05 / 19:07 两次重发同一个 677MB 文件）

```
v5 分片发送开始 launchermap_3.9.151-20260930.apk size=677501607 segs=16
v5 分片[1/16] 完成 … 对端未回片级终态，但 41/41 块已全部确认且连接未断（兼容模式）
…（16 片全如此）…
v5 分片发送完成 launchermap_…（16 片，677501607 B）
```
→ 本机 16/16 全绿，**对端却报失败**。

## 根因：每片数据发完后**没有补发片级 FS_END 结束帧**

接收端判定「一片结束」靠的是 **FS_END 帧**，不是「累计收满 len 字节」：

| 证据 | 出处 |
|---|---|
| 本机 `receiveSegment` 片内循环第一步就是 `if (cmd === LCmd.FS_END) break;` | `V5Transfer.ets:1119`（当初照 1.35 `Lo2/n` 逐条对齐写的） |
| 1.35 侧同语义：收满数据后还要再读一帧，读到 FS_END 才退出循环，然后才 `z()` 写 5、`B()` 写 2/3 | 本机对齐注释（`V5Transfer.ets:1013-1026`） |
| 发送侧 `sendOneSegment` 发完最后一块后**直接进应答循环**，中间没有任何结束帧 | `V5Transfer.ets`（5.0.24 及更早） |

而 1101 单连接通道 `sendPlain` **每个文件都发**这一帧（`endFrame.setStreamCmd(LCmd.FS_END)`，`V5Transfer.ets:433-436`）——分片通道漏了。

因果链：
对端收完 41 块（每块回一个 `5`）→ 继续 `read()` 等片尾帧 → 我们没发 → 它既不回 `5` 也不回 `2`
→ 16 片全部「块已确认、终态不来」→ 5.0.24 兼容判定误判成功并 `close()`
→ 对端 `read` 异常/EOF → **对端报接收失败**（本机日志全绿）。

**排除项**（都核对过，不是原因）：
- 块数 `41` = `ceil(42343850 / CHUNK 1048564)` 精确吻合 → 数据块数与 ack 数一致；
- 1.35 `q()` 对帧2 的解析顺序 `g()J / i() / i() / d()I / d()I / g()J / g()J`
  = fileSize / name / segId / idx / total / start / len，与本端发送**完全一致**
  （`docs/forensics/dump_q.txt:359-372`）→ 元数据无错位；
- 1.35 接收缓冲 `const/high16 v2, 1048576`（`dump_q.txt:343`）→ 与 `CHUNK+12 = 1048576` 对齐。

## 改动（三处）

1. `sendOneSegment`：数据块发完后补发 `FS_END`（`new V5Enc(64)` + `setStreamCmd(LCmd.FS_END)`）。
2. `receiveSegment`：新增 `sawEnd` 标志；若因**收满 len** 退出循环（没读到 FS_END），
   循环**外**补消费那一帧（5s 超时，兼容不发的旧对端）。
   ⚠️ 不改会出新问题：残留字节令 `close()` 时内核发 **RST 而非 FIN**
   → 对端 ECONNRESET —— 与 5.0.20「文件结束帧」是**完全同构**的坑。
3. `AppScope/app.json5`：`5000024 → 5000025`、`5.0.24 → 5.0.25`。

补丁脚本：`docs/patch_scripts/patch_v5025_seg_endframe.py`（哨兵幂等 + 全量校验后统一落盘）。

## 5.0.30 —— 消除输入框与键盘之间那条空白（vivi 截图反馈「输入框抬太高了」）

### 现象
5.0.29 顶栏、底栏都固定住了，但输入框上方**多出一条 ~84vp 的空白**，
输入框不贴键盘上沿。

### 根因：让位高度多垫了一段

| 项 | 说明 |
|---|---|
| `keyboardHeightChange` 语义 | h = **屏幕底 → 键盘顶** 的距离 |
| padding 加在哪 | `TabContent`（不是 Tabs）|
| TabContent 底边位置 | 屏幕底 − 底部安全条(bottomInset) − tab 栏(50vp) |
| 后果 | 再垫 h ⇒ 输入框被抬到「键盘顶再往上 50+34」，正是那条空白 |

**判据**：量空白高度 ≈ 84vp ≈ `50 + 34`，与「tab 栏 + 安全条」吻合 —— 说明是重复让位，不是键盘报值错。

### 修法

```ts
const totalVp: number = px > 0 ? this.getUIContext().px2vp(px) : 0;
const reserved: number = 50 + this.bottomInset;   // tab 栏(.barHeight) + 底部安全条
const vp: number = px > 0 ? Math.max(0, totalVp - reserved) : 0;
this.keyboardVp = vp;
Log.i(TAG, `键盘: px=${px} total=${totalVp}vp 扣除=${reserved}vp 实垫=${vp}vp`);
```

顺带留了日志：下次再遇到让位偏差，**直接看 hilog 里 `键盘: px=…` 这行**，
不用再靠截图量高度。
