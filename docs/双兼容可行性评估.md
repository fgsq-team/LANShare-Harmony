# 「单版本双兼容」可行性评估
### 目标：一个版本同时兼容【官方版 LANShare】与【局域网互传 1.35 / V5 版】

> 评估日期：2026-10-01
> 取证依据：官方 Git 源码 `LANShare-main`（1.2.9_dev）+ `LANShare_1.2.8.apk` 反编译 +
> `局域网互传V5_1.35.apk`(ls135_v5) 反编译 + 鸿蒙工程 `LANShareV5` 现状

---

## 结论（先看这个）

**✅ 可行 —— 而且鸿蒙 V5 已完成约 90%。**

| 能力 | 现状 |
|---|---|
| 接收官方（v4） | ✅ **已实现**（`FileTransfer.receive`，标注「对拍通过」） |
| 接收 1.35（v5） | ✅ 已实现（`V5Transfer.receive` + 1110 分片） |
| 发送 1.35（v5） | ✅ 已实现 |

| UDP 发现 | ⚠️ 结构理论一致，待实测 |

**唯一实质缺口 = 发送侧加一个按对端 `dataVersion` 的分流（约 20 行）。**

## 二、唯一断点：官方按 dataVersion 分流，V5 发送侧没做

官方 `handleVersion()`（源码 637-673）的规则是：

```java
if (cmd == NEW_VERSION_4)            → v4（fileServer.handleVersion1）
else if (device.dataVersion < 4)     → 旧协议
else                                 → T.s("不支持的版本")     // dataVersion≥4 且 cmd≠-2
```

所以两端行为分别推演：

| 方向 | 过程 | 结果 |
|---|---|---|
| **官方 → V5** | 官方 `handleSend` 看 V5 广播的 `dataVersion=5`，`5 ≥ 4` → 用 v4 发（`-2`+JSON）→ V5 的 `handleV4` 收 | ✅ **协议上应已通** |
| **V5 → 官方** | V5 现在硬编码发 v5 帧（cmd=1101/1110，dataVersion=5）→ 官方判「**不支持的版本**」 | ❌ **断在这里** |

**这就是「V5 和官方不互通」的直接原因。** 与 1.35 自身也是同理 ——
1.35 没有 v4 实现，官方发给它走 v4 也收不了，所以 1.35 ↔ 官方 双向都不通。

## 三、改法（精确到行）

**位置**：`entry/src/main/ets/service/LanService.ets` 发送入口（当前 1880-1889）

```ts
try {
  // ★ v5（1.35）发送：字节序列与局域网互传 1.35 修改版逐位对齐。
  return await V5Transfer.send(this.self, dev, files, false,
    (r: TransferReport) => this.onTransferReport(r));
}
```

**改为**（对齐官方 `handleSend` 的语义）：

```ts
try {
  // ★ 按对端协议代次分流（对齐官方 LANService.handleSend 1234-1236）
  //   官方系列 dataVersion = 4 → 用 v4（-2 + JSON，裸序列化）
  //   1.35 / V5   dataVersion = 5 → 用 v5（12 字节头 + 1110 分片）
  const dv: number = dev.dataVersion ?? 0;
  if (dv >= 4 && dv < 5) {
    return await FileTransfer.send(this.self, dev, files, false,
      (r: TransferReport) => this.onTransferReport(r));
  }
  return await V5Transfer.send(this.self, dev, files, false,
    (r: TransferReport) => this.onTransferReport(r));
}
```

**可用性已验证**：`FileTransfer.send(self, target, files, encData, onReport)` 与
`V5Transfer.send(...)` **签名完全一致**，可直接互换（`service/FileTransfer.ets:115`）。

> 若还想要对**旧协议**（官方 1.2.8 之前的版本，dataVersion < 4）兼容，
> 需要额外补旧协议的文件收发（`DataPacket` 12 字节头 + `0x45` 混淆路径）。
> 但官方 1.2.8 本身已是 v4，**属可选**。

## 六、如果目标其实是「安卓版」双兼容

若想做的是**安卓端**一个版本同时兼容官方与 1.35，则方案是：
在 1.35 修改版代码里**补 v4 分支**（即把官方的 `NEW_VERSION_4` 握手 +
`FileSend/FileServer` 的 v4 实现加回去），因为 1.35 现在**完全没有 `-0x2`**。
工作量**明显大于**鸿蒙侧（鸿蒙侧已有现成 v4 实现，只差分流）。

> 两个方向的技术结论相同：**双协议栈 + 按对端 dataVersion 分流**。
> 差别只在于「现成资产」——鸿蒙 V5 已有全套 v4 实现，安卓 1.35 没有。

## 九、实施记录：5.0.8（2026-10-01 13:09 构建）

**结论：双兼容已落地。改动 3 个文件、约 30 行。**（与第六节的预估一致：缺口只有发送侧那一个分流。）

### 改动清单

| 文件 | 改动 |
|---|---|
| `core/LanConfig.ets` | 新增 `V5_MIN_DATA_VERSION = 5`（出站分流的唯一门槛常量）；重写 `DATA_VERSION` 注释（原注释写「与 v4 双向不通」，已过期） |
| `service/LanService.ets#sendFiles` | 硬编码 `V5Transfer.send` → 按 `dev.dataVersion` 分流 |
| `service/TextMessenger.ets#send` | 同上；并修正文件头「说的是 v4、写的是 v5」的过期注释 |

分流代码（`LanService.sendFiles`，消息侧结构同理）：

```ts
const peerVer: number = dev.dataVersion ?? 0;
if (peerVer >= LanConfig.V5_MIN_DATA_VERSION) {
  return await V5Transfer.send(this.self, dev, files, false, cb);   // v5 帧（1101 / 1110）
}
return await FileTransfer.send(this.self, dev, files, false, cb);   // v4 裸序列化
```

### 为什么只改了出站

接收侧**本来就是双栈**——迁移阶段已经做好，这正是本次改动能这么小的原因：

| 入口（`handlePrivateProtocol`） | 触发条件 | 去向 |
|---|---|---|
| v4 | MAGIC 之后首 4 字节 == `-2` | `handleV4` → `FileTransfer.receive` / `onMessageV4` |
| v5 | 首 4 字节 ∈ {1101, 1105, 1110} | `handleV5` → `handleV5Share` / `handleV5Message` / `handleV5Segment` |

### 三个被排掉的风险（都找到了硬证据，非推断）

1. **UDP 发现层能不能互认？能。**
   官方 `udpServer`（1910-1927）先用明文 MAGIC 判分流，再
   `System.arraycopy(data, 4, buff, 0, …)` **去掉 MAGIC** 后才解混淆；
   `DataDec.HEADER_LEN = 12`、`getCmd() = getInt(0)`。与 V5 的
   `V5Udp.parse`（查 MAGIC → `subarray(4)` → 逐字节解）**逐行同构**。
2. **V5 多写的「已知设备表」会不会把官方搞乱？不会。**
   官方 `handleUdp` 读完 8 个设备字段就 `addDevice()`，
   对 cmd=1001/1002/1003 不再读任何尾部字节 → 多余数据堆在不被读的区域。
   反方向，V5 读官方包时 `dec.int()` 在 `remaining < 4` 时返回 0 → `knownCount = 0` → 不读表。
   补充：V5 广播时 `known` 传的就是空数组，所以 `knownCount` 恒为 0。
3. **`FileTransfer.send`（v4）能不能被官方认？能。**
   官方 `handleTcp`（581-587）`readInt()==-2` → `readString()` 读设备 JSON → `handleVersion1`；
   `Device.fromJsonString` 的 11 个字段名与 `DeviceCodec.toJson` **逐字一致**。

### 一个得记住的坑：注释与实现脱节

`TextMessenger.ets` 的文件头注释一直写着「v4 协议」
（`int(-2) + string(json) + int(1105) + boolean(isClip) + string(enc)`），
但实际实现已改成 **v5 单帧**（`V5Header.write` + `enc.string`，**无 isClip**）。
**本次实现直接以实际代码 + 官方源码为准，不信注释**；注释已同步修正。
