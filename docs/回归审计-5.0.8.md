## A 组：已真机验证通过（5 项）

### 1. 发文件崩溃 `Cannot read property length of undefined`
- **根因**：ArkTS 的 `util.TextEncoder.encodeInto('')` 返回 **`undefined`**（非标准 WHATWG 的空 Uint8Array），
  直接取 `.length` 抛异常。崩溃点在「构造文件清单帧」时对 `extra` 字段调 `string('')`。
- **修复点**：`core/V5Codec.ets:152-161`，`V5Enc.string()` 空串/undefined 特判，只写 4 字节长度 0。
- **验证**：用户反馈「手机给 1.35 文字、图片、文件都能发送成功」→ 发送路径全通，无崩溃。

### 2. UDP 互相发现不了（V5↔V5 / 与官方）
- **根因**：V5 的 UDP 混淆误写成「链式 prev」，连 V5↔V5 都还原不回来。
- **修复点**：`core/V5Codec.ets:435-446`，`V5Udp.obfuscate/deobfuscate` 改为**逐字节独立**
  `b[i] = ((b[i]-1) ^ 69) & 0xFF` / `((b[i] ^ 69) + 1) & 0xFF`（0x45 = 69）。
- **交叉验证**：官方源码 `utils/DataEnc.java` 的 `encData()` 正是 `(byte)((b-1)^0x45)` —— 同源同值。
- **验证**：设备间能互相发现并互发。

### 3. 1.35→V5 收图 size=0
- **修复点**：`service/V5Transfer.ets` 的 1101 清单/文件体接收链路（`recvBody` 按声明 size 落盘）。
- **验证**：用户反馈「1.35 给手机……图片成功」。

### 4. 私有协议分流漏判
- **根因**：早期只按 DataEnc 老包解析，Android v4/v5 首帧被判成未知协议直接断开。
- **修复点**：`service/LanService.ets:1312-1337`，先读 4 字节分流：
  `NEW_VERSION_4(-2)` → v4；`1101/1105/1110` → v5；其余 → 老版 DataEnc 包。
- **验证**：真机 hilog 可见「协议代次：v5」正常分流。

### 5. 1.35→V5 发文件失败
- **根因**：1.35 修改版把「文件」走命令 **1110（16 分片并发）**，V5 只实现了 1101/1105，
  16 条连接全被当成「非 v4/v5」拒绝（日志 `first4=1110 hex=00000456`）。
- **修复点**：
  - `core/LCmd.ets`：新增 `FS_SEG_FILE = 1110`；
  - `service/LanService.ets:1331` 分流放行 1110；`handleV5Segment`（1502 起）解析设备头 + encData；
  - `service/V5Transfer.ets`：`receiveSegment` 按 `start` 随机写、`sendByte` 应答。
- **验证**：用户反馈「**能成功**」（5.0.4）。

## B 组：代码已修 / 已实现，但尚未真机验证（5 项）

> 这 5 项全部登记在 `docs/PENDING_TEST.md`。**装 5.0.8 一个即可覆盖**（5.0.8 是在 5.0.7 基础上继续改的）。

### 6. 进度条走一半就判完成
- **根因**：旧实现用「已覆盖到的**最大末端偏移** `maxEnd`」同时算进度和判完成。
  16 片并发乱序到达，只要「落在文件末尾的那一片」先到，`maxEnd` 立刻 = fileSize →
  进度条在 ~50% 处直接判完成并清零；且旧实现此时还会 `segs.delete(segId)`，后到的片会**另建一个文件**。
- **修复点**：`service/V5Transfer.ets:93-95, 978-994`
  —— `SegPart.received` 按 `idx` 去重累加**真实字节数**，进度单调递增、完成判定与到达顺序无关；
  收齐后保留条目（`finishedAt`）做超时清理，迟到片仍能认领。

### 7. 手机→1.35 未走 16 分片
- **背景**：这不是 bug —— 1.35 有资格判定：**仅普通文件且 `size >= 128MB`（`0x8000000`）才走 1110**，
  `MediaInfo/UriFileInfo/StreamInfo` 三类恒不 eligible。
- **修复点**：`service/V5Transfer.ets`
  - `SEG_TOTAL = 16` / `SEG_MIN_SIZE = 134217728`（129-131）；
  - `send()` 分流器（143 起）：`segEligible()` 命中 → `sendSegBatch`（1110，16 片并发）；
    否则 → `sendPlain`（1101，**原实现一行未改**）；
  - `segEligible()`（195-201）：非普通文件直接 false。

### 8. 1110 帧1 缺整段设备头
- **根因**：1.35 的 `E()`（LANService 3266）第一步调 `r(Device,int)`，而 `r()` 是
  「new 编码器 → **写完整设备头** → 返回编码器」。所以帧1 = `[1110][1][len]` + **设备头** + `0x00`，
  之前实现只发了 `[1110][1][1] + 0x00`，少一整段设备头 → 1.35 解析越界错位。
- **修复点**：`service/V5Transfer.ets:537-541`
  ```ts
  const f1: V5Enc = new V5Enc(512);
  f1.reset(LCmd.FS_SEG_FILE, 1);
  V5Transfer.writeHeader(f1, self);   // ★ 补设备头
  f1.byte(0);
  ```
  顺带修正帧2 头部为 `[0][0][len]`（1.35 用 `new q2.c([B)`，**没调 `g()`**，头部保持数组默认 0）。

### 9. 分片应答只读 1 字节 → close 发 RST
- **根因**：1.35 每片写的是**两个**字节 —— `z()` 先写 `5`（FS_NEXT 流控），`B()` 紧接写 `2`(RECV_OK)/`3`(RECV_FAIL)。
  旧实现 `readExactly(1)` 只拿第 1 个字节（=5）就判定成功并 close →
  **内核发现接收缓冲非空 → 发 RST 而非 FIN** → 1.35 端 `ECONNRESET` → `SEG-DONE status=BROKEN`。
- **修复点**：
  - 发送侧 `service/V5Transfer.ets:615-640`：**循环读、跳过所有 `5`**，只有拿到 `2`(FS_END) 才算成功（超时 30s）；
  - 接收侧（1.35→手机）`service/V5Transfer.ets:970-975`：收完一片回 `5` **再回 `2`**，失败回 `3`，
    与 1.35 的 `z()`+`B()` 完全对齐。

### 10. 单版本双兼容（官方 v4 + 1.35 v5）
- **根因**：官方 `LANService.handleVersion()` 有拒绝分支 —— 首帧不是 `-2` 就不看 dataVersion、直接丢弃。
  V5 之前无脑发 v5 帧（`cmd=1101`），在门口就被挡；与数据格式对错无关。
- **修复点**：
  - `core/LanConfig.ets`：新增 `V5_MIN_DATA_VERSION = 5`；
  - `service/LanService.ets:1881-1897`（文件）+ `service/TextMessenger.ets:122-148`（消息）：
    按**对端广播的** `dataVersion` 分流 —— `>= 5` → `V5Transfer.send`，否则 → `FileTransfer.send`（v4）。
- **接收入口本来就已双栈**（`handleV4 → FileTransfer.receive / onMessageV4`），故改动仅出站约 30 行。
- **兼容性硬证据**：UDP 去 MAGIC 偏移（官方 `udpServer` `arraycopy(data,4,…)`）、混淆 `(b-1)^0x45`、
  TCP 常量 `-2/1101/1102/MAGIC`、设备 JSON 11 个字段名 —— 逐项对齐。

## 过程中顺带排掉的「伪问题」（不用改）

| 怀疑点 | 结论 |
|---|---|
| 分片块大小 V5=1048564 vs 1.35=2097140 | `o2/b` 按帧头 len 读，`0x1FFFF4` 只是上限校验，合法 |

| 帧2 字段顺序 | `fileSize/name/segId/idx/total/start/len` ✓ |

| 完成判定 | `o2/u.b()` = `e++ >= total(16)` ✓ |
