## 二、权限映射（`module.json5`）

### 2.1 为什么「装完一个权限弹窗都没有」——不是 bug

**直接读 SDK 定义文件得出的结论**，不是推测：

```
D:\Downloads\commandline-tools-windows-x64-26.0.0.851\command-line-tools\sdk\
  default\openharmony\toolchains\lib\PermissionDefinitions.json
```

| 权限 | `grantMode` | 含义 | 会不会弹窗 |
|---|---|---|---|
| `ohos.permission.INTERNET` | `system_grant` | **安装时静默授予** | ❌ 不弹 |
| `ohos.permission.GET_NETWORK_INFO` | `system_grant` | 安装时静默授予 | ❌ 不弹 |
| `ohos.permission.VIBRATE` | `system_grant` | 安装时静默授予 | ❌ 不弹 |
| `ohos.permission.NFC_TAG` | `system_grant` | 安装时静默授予 | ❌ 不弹 |
| `ohos.permission.CAMERA` | `user_grant` | 需代码调用 `requestPermissionsFromUser` | ⚠️ **声明了但没请求 → 不弹** |
| `ohos.permission.APPROXIMATELY_LOCATION` | `user_grant` | 同上 | ⚠️ **声明了但没请求 → 不弹** |
| `ohos.permission.READ_WRITE_DOWNLOAD_DIRECTORY` | `user_grant` | 同上 | ✅ **点「开始共享」时请求** |

**结论**：局域网文件传输真正需要的 `INTERNET` 是 `system_grant`，安装那一刻就已经拿到，
系统**设计上就不会弹窗**。这不是权限没生效，是根本没有可弹的东西。
唯一需要用户在运行时点「允许」的是 `READ_WRITE_DOWNLOAD_DIRECTORY`（为了让收到的文件
直接落盘到下载目录，而不是每收一个文件弹一次保存对话框），
这条由 `service/PermissionGate.ets` 在「开始共享」流程里发起。

> ⚠️ 排查提示：如果真机上连**下载目录**那条也没弹，先确认是不是**装完就没点过「开始共享」**——
> 权限请求挂在那个动作上。另外若之前已授权过（含授权后重装），系统会记住，
> 再点就不会重复弹窗，属正常。

### 4.1 两套并存的 TCP 编码（**这是真机「Android 发不进来」的根因**）

LanShare 的 TCP 上有**两套完全不同的编码**，靠首 4 字节分流：

| | 旧协议（`dataVersion < 4`） | **v4 协议** |
|---|---|---|
| 开头 | 4 字节魔数 → DataEnc 包（12B 头） | 4 字节魔数 → **裸 int `NEW_VERSION_4 = -2`** |
| 混淆 | 全段 `0x45` 混淆 | **无混淆** |
| 命令 | 在 8 字节包头里 | 裸 int，写在流里 |
| 字符串 | `putString`（4B 长度 + UTF-8） | 一样 |
| 结构 | 一个包一个命令 | 一条流顺序写多字段，长度由业务字段自带 |

> ⚠️ **第一版鸿蒙实现只做了旧协议**，收到 Android 端发来的 `NEW_VERSION_4`（`FF FF FF FE`）
> 会按 12 字节包头的 `cmd` 去解析，得出一个乱码命令码，然后当「未知协议流量」直接断开连接。
> 现象就是：**能发现设备，但一发文件就失败**。
>
> 修复位置：`service/LanService.ets` → `handlePrivateProtocol()` 里先读 4 字节判代次，
> 命中 `NEW_VERSION_4` 转 `handleV4()`；否则 `unshift()` 回退给旧协议解析。

### 4.2 v4 文件收发序列（逐行取自 `FileSend.java` / `FileServer.java`）

发送侧：
```
MAGIC_NUM(4B)
int  NEW_VERSION_4 = -2
str  deviceJson
int  FS_SHARE_FILE (1101)
bool encData
str  transferJson
↔    int 等待应答，必须 == FS_AGREE
重复: int length + bytes（逐文件，encData=true 时 FileCrypto 变换，index 按文件内累计偏移）
```

接收侧：**没有结束标记**，按声明的 `length` 收够即停；`length <= 0` 即中止。
（取自 `FileServer.recvStreamToFile()` —— 这里踩错会表现为「最后一个文件卡住」）

### 4.5 ⚠️ socket 层的四个坑（全部已在真机上暴露过）

#### 坑 1：`listen()` bind 失败会**静默换端口**

`TCPSocketServer.listen()` 的官方注释原文：

> The server uses this API to perform the **bind**, **listen**, and **accept** operations.
> **If the bind operation fails, the system randomly allocates a port number.**

**它不抛异常**。所以「端口被占用 → bind 失败 → 系统换随机端口」这条路上，
你的 `await listen({port: 5856})` 会**正常返回**，而实际监听的是个随机端口。
界面照旧显示 `http://192.168.x.x:5856`，但外部设备永远连不上。
叠加第二个因素更致命：旧实现的 `stop()` **从未调用 `server.close()`**，端口永不释放，
第二次点「开始共享」必然 bind 失败。

修复（`net/LanTcpServer.ets`）：
1. `listen()` 之后**强制回读**真实端口（`getLocalAddress()`）并与期望值比对，不符即中止；
2. `stop()` 改为 `async`，**必须 `await server.close()`**，并逐个 `await chan.closeAsync()`；
3. 把失败原因（`ListenResult.detail`）透传到界面，不再只显示一个「已启动」；
4. UI 展示的端口改用**实际绑定端口**，不再用配置值（`LanService.emit()`）。

#### 坑 2：`on('connect')` 必须在 `listen()` **成功之后**注册

SDK 注释原文：

> `on(type: 'connect', callback: Callback<TCPSocketConnection>): void;`
> **NOTE: This API can be called only after `listen` is successfully called.**

第一版写成了「先注册回调，再 listen」（当时的想法是「别错过第一个连接」），
**与官方前置条件正好相反**。后果是 accept 回调可能根本不触发：
连接被内核排进 accept 队列，但没有任何代码去读它，
客户端表现为**连上了、却永远等不到响应** —— 这正好是
「网页打不开」+「别的设备发不进来」两个症状的共同形状。

现在改为 `await listen()` 成功之后再注册。

#### 坑 3：**TCP 握手成功 ≠ 应用层能收到连接**（假绿灯）

这是最难自查的一个。`connect()` 只要能完成 SYN / SYN-ACK / ACK 就会成功，
而这三步是**内核**做的，跟我们的 `on('connect')` 回调有没有触发**完全无关**。
即使应用层一行 accept 代码都没跑，连接照样「连得上」——只是永远没人应答。

所以第一版那个「本机自连 127.0.0.1 成功 → 自检通过」是**假绿灯**：
它只证明了端口在内核里开着，完全没碰应用层。**这一点是在真机上被推翻的**。

**改法**：`e2eSelfTest()` 改成真端到端，三步全过才算通过：

| 判据 | 证明了什么 | 失败说明 |
|---|---|---|
| 自连 `127.0.0.1` 成功 | 内核层面端口是开的 | 监听根本没生效 |
| `accept` 计数增加 | **应用层真的拿到了连接** | accept 回调没触发（坑 2） |
| 收到 HTTP 响应字节 | 业务路由真的在干活 | 分流对了但 HTTP 没响应 |

失败时直接输出「最先失败的那一环」，例如：

```
监听 0.0.0.0:5856，但自检未通过：端口在听，但应用层收不到连接（accept 回调未触发）——外部设备同样连不上
```

这句话本身就是排查结论，不用再靠猜。UI 上另加「重新自检」按钮，不重启服务即可取当前结论。

#### ★ 坑 4（**真机三个症状的共同根因**）：accept 循环把业务处理当成了同步的

这条是致命的，而且一开始完全没看出来。`LanTcpServer` 原先是这么写的：

```ts
// ChannelHandler 声明成返回 void
export interface ChannelHandler {
  handle(channel: TcpChannel, kind: number, head: Uint8Array): void;   // ← 问题在这
}

private async dispatch(channel: TcpChannel, client: socket.TCPSocketConnection): Promise<void> {
  const head = await channel.readExactly(4, 15000);
  ...
  this.handler.handle(channel, kind, head);   // ← 没有 await，而且也无从 await
  // dispatch 到这里就返回了
}

// 调用处：
this.dispatch(placeholder, client).then(() => {
  placeholder.close();          // ← 业务才刚开始，连接已经被关掉
});
```

而 `LanService.handle()` 内部是这样的：

```ts
handle(channel, kind, head): void {
  this.router.serve(channel, head).catch(...);          // 没 await
  this.handlePrivateProtocol(channel).catch(...);       // 没 await
}
```

**后果**：`dispatch` 一返回，`placeholder.close()` 立刻把通道 `closed = true`，
此时业务代码**连第一个字段都还没读完**。三个真机症状全部由此而来：

| 症状 | 在这条 bug 下的成因 |
|---|---|
| **网页打不开** | `router.serve()` 刚起来就被关连接，浏览器收不到任何响应字节 |
| **别的设备发不进来** | v4 读到一半通道被关，Android 端只能看到「连接被对端关闭」 |
| **发给别人立刻失败（同一秒）** | 发给自己的那一次，服务端瞬间关连接，客户端立刻收到 close |

最后一条还是定位这条 bug 的**关键指纹**：
「同一秒失败」只可能是**对端主动断开**，不可能是超时（超时必然是 15 秒整）。
把「同一秒」和「15 秒整」两个时间戳分开看，就能直接排除网络问题。

**修法**：

1. `ChannelHandler.handle` 的返回类型改成 `Promise<void>`，
   并在注释里写明「**调用方必须 await，因为连接生命周期由处理完成决定**」；
2. `dispatch` 里改成 `await this.handler.handle(channel, kind, head)`；
3. `LanService.handle` 改成 `async`，内部 `await this.router.serve(...)` /
   `await this.handlePrivateProtocol(...)`，异常自己兜住。

> 教训：**在事件回调模型里，「处理函数返回」等于「这条连接可以关了」是一个必须显式约定的契约。**
> 只要有一环漏了 await，症状就是「连上了但永远没响应」——
> 而这和「网络不通」「防火墙」「对端服务没开」长得一模一样。这也正是坑 3 那个
> 假绿灯自检之所以危险的原因：它根本测不到应用层。


### 4.6 真机排障现在能拿到哪些证据

`LanTcpServer` 的关键事件**下沉到 UI 日志**（`setLogSink`）。以前这些只进 hilog，
用户在真机上完全看不到，只能拿别的设备盲试。现在启动一次共享，日志里会依次出现：

```
监听 0.0.0.0:5856，端到端自检通过
新连接来自 192.168.10.100:52341        <- accept 真的发生了
已分流为 LanShare 私有协议              <- 前 4 字节判定结果
协议代次：v4（裸序列化，无混淆）         <- NEW_VERSION_4 判定结果
v4 连接来自 DBY-W09 (192.168.10.100)
v4 命令码 1101                          <- FS_SHARE_FILE
连接处理结束                            <- 业务真的跑完了（坑 4 的直接证据）
```

**有没有 `新连接来自` 这一行，就能一句话定性**：是「没人连进来」还是「连进来了但没处理好」。
**有没有 `连接处理结束` 这一行**，则能区分「处理完了」和「处理到一半连接被关掉了」。

### 4.7 其它已修的真机问题

| 现象 | 根因 | 修法 |
|---|---|---|
| 设备列表第一项是**自己**（`192.168.10.146`），一点「发送文件」就等于发给自己 | UDP 广播会回环到本机，`onDeviceFound` 没过滤 | 按 `uniqueUUid` 优先过滤自己，退化才比对 IP+端口 |

## 八、验证工具

```bash
cd tests/protocol-bytecheck

# 1) 旧协议（DataEnc 混淆包 / UDP）
python compare.py

# 2) v4 协议（MiniJson / FileCrypto / ProtoIO）
python v4_compare.py
```

| 脚本 | 覆盖 | 当前结果 |
|---|---|---|
| `compare.py` + `ref.py` + `check.mjs` | 12 字节包头、`0x45` 混淆、UDP 魔数、int 边界、往返自洽 | **8/8 通过** |
| `v4_compare.py` + `v4_check.mjs` | MiniJson 解析/生成、FileCrypto 变换、ProtoIO 裸序列化 | **83/83 通过** |

要求：
- Node ≥ 22.6（需要 `--experimental-strip-types`，脚本已自动带上）
- Python 3.9+
- 无需 DevEco Studio、无需 Android SDK、无需 Java 运行时

该脚本直接读取**交付的 .ets 源文件**，只替换平台绑定（`util.TextEncoder` → 平台内置同名类，
`TcpChannel` → 桩），不重写任何业务逻辑，所以验证对象就是交付物本身。

**v4 对拍的两个设计要点**（避免「假绿灯」）：
1. **用例清单只有一份**：Node 侧把用例输入原文（`jsonCases` / `quoteCases` /
   样本字节的 hex / ProtoIO 的值表）连同实测结果一起回传，Python 侧据此重算期望值。
   两侧各写一份用例清单迟早会漂移。
2. **JSON 走语义深比较，不走字符串比较**：JS 里所有数字都是 double，
   `1e3` 在 JS 侧打印成 `1000`、在 Python 侧是 `1000.0`，
   拿字符串比会误报。所以解析结果按数值逐层比，`quote`(生成) 才做字符串严格比较
   —— 那里比的正是转义格式本身。

**有意保留的一处分歧**：`MiniJson.MAX_DEPTH = 64`，70 层嵌套会被拒（Python 标准库能解析）。
这是防栈溢出的护栏，已在脚本里作为 `jsonguard:depth-guard` 显式断言，不是 bug。

## 十、真机安装：本仓库的产物是**未签名** HAP

`build.cmd` 产出的是 `entry-default-unsigned.hap`。构建日志里有一行不能忽略：

```
> hvigor WARN: Will skip sign 'hos_hap'. No signingConfigs profile is configured in current project.
```

**鸿蒙真机不接受未签名 HAP**。所以「构建成功」和「能装到手机上」是两件事。

本机环境实测：`C:/Program Files\Huawei\DevEco Studio\` 下**只有 `sdk\default`，没有 IDE 主程序**
（不是完整安装），`%USERPROFILE%\.ohos\config` 也不存在 —— 即本机没有任何签名产物。
`D:/Downloads/commandline-tools-windows-x64-26.0.0.851/command-line-tools` 是命令行工具链，不含签名证书。

### 装到真机的两条路

**路线 A：让 hvigor 直接产出已签名 HAP（推荐，一次配好长期可用）**

在 `build-profile.json5` 的 `app.signingConfigs` 里填一份签名材料，之后 `build.cmd` 就会自动签名：

```json5
"signingConfigs": [
```

| `.p12` 密钥库 | `keytool -genkeypair -alias debugKey -keyalg EC -sigalg SHA256withECDSA -dname "CN=LANShare" -keystore default_LANShare.p12 -storetype pkcs12 -validity 3650`（JDK 自带的 keytool 即可） |

>    手工填写容易被 hvigor 判为非法；最稳的做法是走一次路线 B 让它自己写进去。

### 11.1 结论汇总

| # | 症状 | 状态 | 证据 |
|---|---|---|---|
| 1 | 界面网址别人的电脑打不开 | ✅ 已修好 | 从 PC `curl` 得到 `HTTP/1.1 200 OK` / `Content-Length: 10530` / 0.154s；手机侧同时打出 `新连接来自 192.168.10.186:25603` → `已分流为网页(HTTP)` → `连接处理结束` |

| 3 | 鸿蒙发给别人失败 | ✅ 已定位并修复 | 见 11.2 |

### 11.2 ★ 第 3 条的根因：`transferJson` 里的 `length` 恒为 0

把 PC 伪装成一台 LANShare 设备（UDP 心跳 + TCP 5856 接收端）后，
在手机上点「发送文件」，PC 侧收到**完全正确**的协议序列：

```
═══ TCP 连接来自 192.168.10.146:39220
  魔数 = 0x66677371 ✓
  协议代次 = -2 (NEW_VERSION_4) ✓
  对端设备 JSON (248B): {…"devMode":6…}         ← 鸿蒙正确声明自己
  cmd = 1101 (FS_SHARE_FILE) ✓    encData = false ✓
  传输清单 (421B): {…,"files":[{"name":"entry-default-unsigned (2).hap","length":0,…}]}
  → 回 FS_AGREE
  ✓ 收到 0/0 B
```

**协议全对，唯独 `length: 0`。** 这直接踩中两个坑：

- 接收端逻辑是 `if (fileSize > 0) { 收流 } else { filePath.createNewFile(); }`
  —— 看到 0 就**建个空文件走人**；
- 发送端 `sendOne` 也「按约定」判断 0 字节不必发分片。

**双方都认为成功，用户拿到一个 0 字节文件，而且全程零报错。**

根因在 `service/FileStorage.ets` 的 `OutgoingFile.fromUri()`：
它只从 URI 里取名字和类型，**从未设置 `size`**，
而字段注释写的是「0 表示未知（会先 stat）」—— 那句 stat 从来没写。

修复三处：

1. **`OutgoingFile.fromUri()` 真正去 stat**（`openSync` + `statSync(fd)`，
   与 `FileSource.open` 同一条路径，保证「报给对端的大小」与「实际读出的字节」同源）；
2. **新增 `sizeKnown` 标志**。「取不到大小」是硬错误，**必须**与「真的是 0 字节文件」区分开 ——
   前者在 `FileTransfer.send()` 入口直接拒绝并说明原因，绝不允许静默发出一个空文件；
3. **补一条日志**：清单发出后打
   `已发出文件清单（N 项 / X B），等待 <设备> 应答 FS_AGREE`。
   这条是把「已经告诉对方要发什么」和「还在等对方点头」分开的关键 ——
   少了它，真机上只能看到一句「已连接」，无法判断是没发出去还是对方不理。

### 11.3 顺带修掉：设备 uuid 变成畸形串

真机抓包里鸿蒙上报的 `uniqueUUid` 是：

```
-b98e80984aea8e470c9bf12f-6ea3f251        ← 34 字符，带两个连字符
```

正常应该是 32 位纯 hex。原因在 `LanService.ensureUuid()` 的哈希写法：

```ts
h1 = ((h1 ^ c) * 16777619) % MOD;      // ❌
```

三个问题叠加：

1. `h1 ^ c` 会把 `h1` 折成**有符号 int32**（`2166136261` → `-2128831035`），负数继续乘；
2. JS 的 `%` 与 C 不同，是**保号**的，负数的模仍是负数；
3. `(-x).toString(16)` 输出 `"-7f3a…"`，`padStart(8,'0')` 对负号补位后长度也不再是 8。

修法：`Math.imul(h1 ^ c, 16777619) >>> 0`。
用 `Math.imul` 而不是 `* 16777619`，是因为后者结果可达 7.2e16，
已超出 double 的精确整数范围（2^53）。

**已用 Node 实测对比**：同一台机器的种子，旧算法产出 `len=34 / 非纯hex`，
新算法稳定 `len=32 / 纯hex`。（注意这个 bug 不是必然触发，取决于哈希中间值是否变负 ——
所以它可能「有时好有时坏」，更难查。）

### 11.4 两个不属于代码问题的观察

**① 「没弹权限」的真相**（已在 §二 表格里补了 grantMode 证据）：
`INTERNET` / `GET_NETWORK_INFO` / `VIBRATE` 都是 `system_grant`，安装即静默授予，本来就不该弹窗。

**② 「下载目录」在这个机型上根本用不了。** 真机日志：

```
PermissionGate: ohos.permission.READ_WRITE_DOWNLOAD_DIRECTORY authResult=2 dialogShown=true
file_api: CheckFileManagerFullMountEnable] Not supporting all mounts
file_api: GetUserDownloadDir] Capability not supported
```

`authResult=2` 是「请求非法」，往后追是系统侧 `Not supporting all mounts` ⇒
`Environment.getUserDownloadDir()` 抛 **801（设备不支持）**。
**这不是用户拒绝授权**，所以收到的文件只能落应用沙箱
`/data/storage/el2/base/haps/entry/files/LANShare/`，
**用户在系统文件管理器里看不到**。这件事需要产品决策（见 §十二）。

## 十二、网页访问：「没有访问权限，请在手机上同意之后刷新页面」

### 12.1 现象

浏览器打开 `http://192.168.10.146:5856`，页面本身能返回
（`HTTP/1.1 200` / `Content-Length: 10530`），但网页立刻弹出模态框：

> 没有访问权限，请在手机上同意之后刷新页面

而手机端**根本没有能点「同意」的地方** —— 网页因此永远进不去。

**这不是权限问题。** `INTERNET` / `GET_NETWORK_INFO` 都是 `system_grant`，
TCP/HTTP 早已打通（§十一 已用 curl 独立验证）。真正的原因是：
**鸿蒙端漏实现了原 Android 的「网页客户端授权」流程**，
导致网页与服务端的接口契约对不上。

### 12.2 原 Android 的设计（是特性，不是缺陷）

`web/LHttpServer.java` 的 `/initConfig` + `db/TokenDBUtil.java`（表 `token`：
`id/ip/name/pass/custom/isdel`）构成一套**白名单模型**：

```
浏览器首次访问
  → POST /initConfig（带自己的 IP）
     → 按 IP 查 token 表，查不到 ⇒ 建一条 pass=0 的记录
     → 发 SERVICE_HTTP_NEW_CLIENT 消息 ⇒ 手机端弹「是否允许该设备访问网页」
     → 返回 {rootPath, name, token, pass:false}
  → 网页判定 a.pass 为假 ⇒ 弹「没有访问权限…」⇒ 每 2 秒轮询 POST /checkPass
     → 手机端点「同意」把 pass 置 1 ⇒ /checkPass 返回 {pass:true}
     → 网页 location.reload()，正常进入
```

另有一个全局开关 `Config.WEB_OPEN`（`SettingActivity` 里的
「网页服务开放」）：打开后新客户端直接 `pass=1`，不再需要确认。

### 12.3 真机取证：契约确实是断的

对手机上**当时运行的版本**直接发起网页端的两个请求：

```bash
$ curl -s -X POST -H 'token: probe-token-123' -d '{"test":1}' http://192.168.10.146:5856/initConfig
{"deviceName":"LANShare","udpPort":4573,"tcpPort":5856,"protocolVersion":4,"platform":6}

$ curl -s -X POST -H 'token: probe-token-123' -d '{}' http://192.168.10.146:5856/checkPass
{"ok":true}
```

对照网页真正要读的字段（出处 `resources/rawfile/web/js/lanshare.min.js`）：

| 接口 | 网页要什么（出处） | 实机给的是什么 | 后果 |
|---|---|---|---|
| `POST /initConfig` | `{rootPath, name, token, pass}`（:195-198） | `{deviceName, udpPort, …}` | `a.pass === undefined` → 判定「没权限」 |
| `POST /checkPass` | `{pass}`（:181） | `{ok}` | `b.pass` 永远是 `undefined` → **死循环** |
| `POST /updateWebName` | 请求体 `{webName}` JSON（:170） | 按 urlencoded 读 `name` | 改名无效 |
| `POST /files` | 响应 `{path, list:[{name,path,isDirectory,time}]}`（:376-400） | `{dir,count,items:[{isDir,size}]}` | 即使授权通过，列表也是空的 |

**四个接口全错位，其中 `pass` 缺失是致命的一条** —— 它让网页停在提示框上永远出不来。

> 注意：`/files` 网页用的是 **POST + JSON body**（`{path, isBack}`），不是 GET 查询串；
> `/file/<名字>` 的真实路径在 **`?path=` 查询参数**里（:114 / :218），URL 路径段只是文件名。

### 12.4 修复

**① 新增 `service/WebClientStore.ets`（替代 `db/TokenDBUtil.java`）**

字段一一对应：`token/ip/name/pass/custom/createdMs/lastSeenMs`，
用 `preferences` 存一份 JSON 数组（鸿蒙侧不需要引入三方 SQLite）。
提供 `byIp()` / `byToken()` / `add()` / `setPass()` / `updateName()` / `remove()` / `pending()`。
超过 64 条时按 `lastSeenMs` 淘汰（**不淘汰还在等确认的记录**）。

**② `HttpRouter` 三个接口对齐原语义**

| 接口 | 现在的行为 |
|---|---|
| `/initConfig` | 按 IP（退而按 token）查白名单；新客户端建记录并回调 UI；返回 `{rootPath, name, token, pass, deviceName, tcpPort}` |
| `/checkPass` | 按 `token` 头查白名单，返回 **`{"pass":true/false}`** |
| `/updateWebName` | 解析 JSON `{webName}`，改的是**该网页客户端**的名字（不是本机设备名） |

`rootPath` 取 `${filesDir}/LANShare` —— 必须落在 `resolveSafePath` 允许的范围内，
否则网页一导航就被 403。

**③ `/files` 与 `/file/*` 按网页格式重写**

- `/files` 支持 POST + JSON body `{path, isBack}`（GET `?dir=` 保留供 curl 调试），
  返回 `{path, list:[{name, length, path, isFile, time:"yyyy-MM-dd HH:mm:ss", isDirectory}]}`；
  目录优先排序；断链的符号链接跳过而不是整表失败。
- `/file/*` 优先从 `?path=` 取绝对路径，取不到才退回 URL 路径段。
- `/media` 返回 **`[]`**、`/apps` 返回 **`{"list":[]}`** —— 网页对这两个接口是
  `.forEach()` / `a.list`，返回对象会让前端直接报错，返回空集合则页面正常渲染。

**④ UI：`Index.ets` 新增授权区**

- 「网页访问免确认」开关（对应原 `Config.WEB_OPEN`，持久化到 preferences 文件 `lanshare_web` 的 `webOpen` 键）；
  打开时**一并放行当前所有待确认客户端**，否则用户会以为开关没生效。
- 待确认客户端卡片：显示 IP + 名字 + 「拒绝 / 允许」两个按钮。
- 有新客户端时写一条 UI 日志：「有新设备请求访问网页：x.x.x.x（名字）— 请点「允许」」。

**⑤ 一个细节**：`/files` 原来那段「过滤隐藏文件」的条件是反的
（`if (showHiddenFiles) { if (name.startsWith('.')) continue; }` —— 只有开启「显示隐藏文件」
时才过滤）。已按直觉修正为始终不展示隐藏文件。

### 12.5 验证（`tests/live-probe/web_auth_check.mjs`，55/55 通过）

脚本**直接执行交付的 `service/WebClientStore.ets`**（Node 22 类型擦除 + 平台绑定 shim），
覆盖四组：

| 组 | 内容 |
|---|---|
| A | 授权状态机 20 项：登记 → 待确认 → `setPass` 放行 → 不同 IP 互相独立 → 改名 → 移除 |
| B | 持久化往返 6 项：模拟重启后 `token/ip/name/pass/createdMs` 全部保留 |
| C | token 唯一性：1000 次生成无重复、全部 32 位纯小写 hex |
| D | 解析网页真实请求体：`{"path":…,"isBack":false}`、`{"webName":"我的笔记本电脑"}`、空 body 不抛异常 |
| E | **网页 ↔ 服务端键名一致性静态断言**：`initConfig` 的四个字段、`checkPass` 的 `pass`、`files` 条目的六个字段，逐项在服务端源码里断言存在；反向再断言网页 JS 确实在读这些键 |

E 组是这次的核心护栏 —— 它把「网页读什么」和「服务端给什么」钉在一起，
将来任何一边改动导致错位都会立刻红。

运行：

```bash
cd tests/live-probe
node --experimental-strip-types web_auth_check.mjs
```

## 十三、为什么这台机型不支持「下载」目录

### 13.1 结论

**不是权限问题，是设备形态问题。**

`Environment.getUserDownloadDir()` 需要系统能力
`SystemCapability.FileManagement.File.Environment.FolderObtain`。
该能力**官方仅对 PC/2in1 与 Tablet 形态提供**，手机形态没有实现。

SDK 声明（`sdk/default/openharmony/ets/api/@ohos.file.environment.d.ts`）：

```ts
/**
 * Obtains the sandbox path of the pre-authorized **Download** directory.
 * @permission ohos.permission.READ_WRITE_DOWNLOAD_DIRECTORY
 * @throws { BusinessError } 801 - Capability not supported.
 * @syscap SystemCapability.FileManagement.File.Environment.FolderObtain
 */
function getUserDownloadDir(): string;
```

官方文档对 `getUserDownloadDir` / `getUserDesktopDir` / `getUserDocumentDir`
三个接口均标注「**Currently, only 2-in-1 devices are supported**」。

### 13.2 本机的实测证据

```bash
$ hdc shell param get const.product.devicetype
phone                                    ← ★ 形态是 phone，不是 tablet / 2in1
$ hdc shell param get const.product.model
PLR-AL50                                 ← HUAWEI Mate 70 Pro 优享版
$ hdc shell param get const.ohos.fullname
OpenHarmony-7.0.0.105
```

系统侧日志给出同一结论：

```
E environment_n_exporter.cpp:84  CheckFileManagerFullMountEnable] Not supporting all mounts
E environment_n_exporter.cpp:186 GetUserDownloadDir] Capability not supported
```

### 13.3 为什么之前看起来像「权限申请不上」

早期实现直接去申请 `ohos.permission.READ_WRITE_DOWNLOAD_DIRECTORY`，
拿回来的是 `authResult = 2`（请求非法），现象非常容易被误读成
「权限名写错了 / `module.json5` 声明有问题」。实际上：

- **能力不存在** ⇒ 无论有没有权限都调不通；
- 而权限申请在能力缺失时会以「请求非法」快速失败，而不是弹窗让用户点。

**修法：把顺序调过来 —— 先查能力，再申请权限。**

```ts
if (!canIUse('SystemCapability.FileManagement.File.Environment.FolderObtain')) {
  // 说明「设备形态不支持」，不要再去申请权限
  // 否则拿回 authResult=2，把人引向「权限配置错误」的错误方向
}
```

`PermissionGate.supportsUserDownloadDir()` 与 `FileStorage.tryDownloadDir()`
现在都以此为先决条件，UI 文案也改成：

> 接收文件保存到：应用沙箱（系统文件管理器中看不到）：本机不支持预授权目录
> （官方仅 PC/2in1 与平板提供该能力）

### 13.4 产品上的三个可选方向（待定）

手机形态上，收到的文件只能落沙箱
`/data/storage/el2/base/haps/entry/files/LANShare/`，**用户在系统文件管理器里看不到**。
三种处理方式：

| 方案 | 用户操作 | 代价 |
|---|---|---|
| **A. 接收后提示实际路径 + 一键复制** | 无 | 用户仍需用其他方式取走文件；对"局域网传文件到手机"这个主场景**体验不完整** |
| **B. 接收完弹「另存为」走系统 Picker** | 每次接收都要选目录 | 一次授权，之后用户可见；但打断自动接收流程 |
| **C. 用系统分享导出** | 手动分享到目标 App | 适合"马上发给别人"，不适合"存起来" |

推荐 **B 的变体**：首次接收后提示一次，并提供「以后都自动保存到某目录」的持久化授权
（`DocumentViewPicker` 拿到的目录 URI 可以持久化）。
这需要确认鸿蒙侧目录 URI 的持久化能力，属独立任务。

## 十五、网页「连接断开」的真根因：WebSocket 会话层从未接上

### 15.1 现象（vivi 2026-09-30 实测）

浏览器访问 → 手机弹出确认框 → 点「允许」→ **网页一片空白** →
约 15 秒后弹出「连接断开，请启动LANShare后刷新页面」。

### 15.2 取证：先把「另存为完整网页」当证据读

用户提供了一份浏览器「另存为全部」的结果（`LANShare.html` + `LANShare_files/`）。
两个反常点：

| 观察 | 含义 |
|---|---|
| 3 个 `.css` 全部正常保存 | 静态资源服务本身是好的 |
| **10 个 `.js` 全部带 `.下载` 后缀** | 浏览器没把它们当脚本吃进去 |

一开始怀疑 MIME 错了，但**直接向真机要证据推翻了这个假设**：

```bash
curl -D - -o /dev/null http://192.168.10.146:5856/js/jquery.min.js
# Content-Type: application/javascript; charset=utf-8   ← 完全正确
curl -D - -o /dev/null http://192.168.10.146:5856/css/style.min.css
# Content-Type: text/css; charset=utf-8                ← 也正确
```

且两侧文件**字节数完全一致**（jquery 130721 B / lanshare 18587 B ...），不是截断。
**所以 MIME 与传输都没问题，`.下载` 后缀是 Chrome 保存时的行为，不是故障本身。**

### 15.3 读前端源码定位真实触发点

在 `lanshare.min.js` 里找到 `initConfig()`：

```js
if (a.pass) {
    $(".lyear-layout-web").show();   // ← 页面主体靠这句才显示
    initWS();                        // ← WebSocket 在这里建立
    initView()
} else {
    $("#myModal").modal("show");     // ← 「没有访问权限」
    checkPass()                      // ← 每 2 秒轮询一次 /checkPass
}
```

这同时解释了两件事：

1. **「网页空白」**：`.lyear-layout-web` 是 `style="display: none"` 的主体容器，
   只有 `pass === true` 分支才 `show()`。
2. **「连接断开」**：文案来自 `lanshareChat.min.js`

```js
ws = new WebSocket("ws://" + location.host + "/wss?token=" + localStorage.getItem("token"));
ws.onclose = () => { $("#notConnectedModal").modal({backdrop:"static", show:true}) };
```

### 15.4 真机直连取证：握手成功，但连接被自己关掉

用 Node 手工发一次 WebSocket 握手（`tests/live-probe/ws_upgrade_probe.mjs` 同款手法）：

| 请求 | 服务端响应 | 结果 |
|---|---|---|
| `GET /` | `200 OK` + 10530 B HTML | 正常 |
| `GET /wss` + `Upgrade: websocket` | **`101 Switching Protocols` + 正确的 `Sec-WebSocket-Accept`** | **26 ms 后连接被关闭** |

握手**完全成功**，`Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=` 与 RFC 6455 示例值一致。
问题不在握手，而在**握手之后**。

### 15.5 根因：`setSink()` 只有定义，没有调用点

`WsUpgradeRouter` 的设计是「升级成功后把通道交给会话层」：

```ts
static detach(channel: TcpChannel): void {
    if (WsUpgradeRouter.sink !== null) {
        WsUpgradeRouter.sink(channel);
    } else {
        WsUpgradeRouter.pending.push(channel);   // ← 没人来取
    }
}
```

但全工程搜索 `setSink`，**只有 `HttpRouter.ets` 里的定义，零个调用点**。于是：

1. 握手 101 发出 ✓
2. `detach()` → `sink === null` → 通道被塞进 `pending` 数组，**永远无人认领**
3. `handleWsUpgrade()` 返回 `null` → `HttpRouter.serve()` 返回
4. `LanTcpServer.onConnect()` 的收尾：`this.dispatch(...).then(() => placeholder.close())`
   → **连接被自己关掉**
5. 浏览器 `onclose` → 弹「连接断开」

> 这与第十一节的 `ChannelHandler.handle` 是同一类问题：**把「处理函数返回」等同于「连接该关了」**。
> 区别在于 HTTP 是短连接，这个假设成立；WebSocket 是长连接，它不成立。

### 15.6 修复（四处）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `net/NativeSocket.ets` | `TcpChannel` 新增 `detached` 标志 + `markDetached()` |
| 2 | `net/LanTcpServer.ets` | accept 收尾改为 `if (!placeholder.detached) placeholder.close()` |
| 3 | `net/HttpRouter.ets` | `WsUpgradeRouter` 导出；握手后先 `markDetached()` 再 `detach()` |
| 4 | `service/WebSocketSession.ets` | **新增**：会话层（帧读写循环 + 分片 + ping/pong/close） |
| 5 | `service/LanService.ets` | 构造时 `WsUpgradeRouter.setSink(...)`；实现设备列表推送与聊天收包 |

`markDetached()` 必须**在 `detach()` 之前**、且在 `serve()` 返回之前调用 ——
它要赶在 accept 收尾读这个标志之前置位。

### 15.7 会话层协议（与前端严格对齐）

```
服务端 -> 网页  {"cmd":1, isLeft, devName, devType, message, messageType, filePath, fileSize}
               {"cmd":2, "data":[{"address":"<ip>","devName":"...","devIP":"<ip>","devType":0}]}
网页 -> 服务端  {"cmd":1, isLeft:false, devName, message, messageType, selectedDevice, isClip}
```

⚠️ 字段名必须照抄前端：`SYNC_DEVICE_LIST` 里它读的是 `address` / `devName` / `devIP`，
少一个网页上那个下拉框就是空的。

帧层三条硬约束（违反浏览器直接断开）：

- 客户端帧**必须带掩码**（MASK=1），服务端帧**必须不带**
- 长度三档：<126 单字节 / 126 后跟 2 字节 / 127 后跟 8 字节
- 控制帧载荷 ≤ 125 字节且不可分片；分片消息要累积到 `fin` 再交业务

### 15.8 未结

跨设备**聊天转发**仍空着：它依赖私有协议 `FS_MESSAGE` 的编码（v4 与旧版是两套），
尚未从原码提取（见「B1 剩余工作」）。这里**不拿猜测的格式直接发** ——
猜错会让对端收到畸形包甚至断连。当前行为：记日志 + 落库，转发待 B1 补齐。

## 十七、网页卡 15 秒 + 上传失败：两个根因与实测

### 17.1 「打开页面 15 秒后才显示内容」= 响应缺 Content-Length

**现象**：网页的 HTML/CSS/JS 秒开，但 `initConfig` 之后页面主体迟迟不显示，
约 15 秒后才出现内容；点开文件列表同样要等。

**根因**：`HttpResponse.encodeHead()` 从不自动补 `Content-Length`。

HTTP/1.1 判定响应体结束只有两种方式：`Content-Length`，或 `Transfer-Encoding: chunked`。
两者都没有时，浏览器**只能等连接关闭**才知道响应收完了。
而本服务的响应走 keep-alive（`serve()` 发完响应会回到 `readExactly(1, 15000)` 等下一个请求），
连接不会主动关 —— 于是每个 JSON 接口都要卡满 **15 秒**，那正是首个字节读取的超时值。

**为什么只有 JSON 接口中招**：静态资源走 `serveRawFile()`，那里显式 `set` 了
`Content-Length`，所以 HTML/CSS/JS 全部秒开。
这个「静态快、接口慢」的差异本身就是判据 —— 一开始被 `.下载` 后缀带偏，
以为是服务端 MIME 错了，curl 直连真机后才发现 MIME 完全正确。

**证据**（真机 curl，修复前的旧版本）：

| 请求 | 耗时 |
|---|---|
| `GET /`（serveRawFile，**有** Content-Length） | 0.07 ~ 0.19 s |
| `POST /initConfig`（HttpResponse.json，**无** Content-Length） | 等连接关闭，15 s+ |

**修法**：在 `encodeHead()` 里统一补长度。204/304 按规范不得带 body，跳过；
已经显式设置过的不覆盖（`serveRawFile` / `downloadFile` 自己设了准确值）。

**修复后真机实测**：

```
POST /initConfig -> Content-Type: application/json; charset=utf-8
                    Connection: keep-alive
                    Content-Length: 185
POST /checkPass  -> Content-Length: 14
POST /files      -> Content-Length: 702
```

`/initConfig` 从 15 s 降到 **0.15 s**（其中服务端处理 28 ms）。

### 17.2 「上传失败」= 三个问题叠加

| # | 问题 | 后果 |
|---|---|---|
| 1 | `/uploadFile`、`/chatUploadFile` 直接返回 501（未迁移） | 就算 body 收完也失败 |
| 2 | `TcpChannel` 用 `concat(pending, chunk)` 追加数据 | 每来一片就把已有数据整份复制，O(n²) |
| 3 | 上传整体复用 `readExactly` 的 60 秒超时 | 大文件必然中途断 |

**问题 2 的量化**：真机实测 32 MiB 上传耗时 **51.5 秒**，有效吞吐 **0.62 MiB/s**。
分片约 500 次，累计复制量 O(n²) ≈ 8 GiB —— 千兆局域网里跑出 5 Mbps 的观感。

**修法**：

1. **`TcpChannel` 改滑动窗口缓冲**（`buf` + `[head, tail)` 有效区间）：
   追加时空间不足才「压实 + 倍增」，消费只推进 `head`，均摊 O(1)、不产生中间垃圾。
   同时新增 `readSome(maxBytes)` —— 「有多少给多少」的流式接口。
2. **新增 `service/MultipartStream.ets`**：流式 multipart 状态机
   （PREAMBLE → HEADERS → BODY → EPILOGUE），边收边解析边落盘，
   内存占用与文件大小无关。两个要点：
   - BODY 状态必须保留 `marker.length + 1` 字节尾巴不写盘：
     `\r\n--<boundary>` 可能正好跨两个网络分片，少了这步文件里会夹杂被撕裂的分隔符；
   - 文件名按 **UTF-8** 解码：multipart 是二进制安全的，浏览器直接发原始 UTF-8 字节。
3. **`serve()` 里把上传请求提前分流**，不走「先读满 body 再路由」的通用路径；
   上传超时放宽到 10 分钟，且超时时把「已收多少字节」写进给用户的提示。

### 17.3 修复后实测对比

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 1 MiB 上传 | HTTP 501 | **200 OK，453 ms** |
| 32 MiB 上传 | 501，**51.5 s**，0.62 MiB/s | **200 OK，2.05 s，15.63 MiB/s** |
| `/initConfig` | 15 s（缺 Content-Length） | **0.15 s** |
| 并发 8 个 GET | 101 ms | 64 ms |

**吞吐提升 25 倍。** 落盘日志（字节数分毫不差）：

```
MultipartStream: 收下一个分段: probe.bin (1048576 B)
HttpRouter: 网页上传落盘: .../LANShare/其他/probe.bin (1048576 B)
HttpRouter: 网页上传完成: 1 个文件 / 1048576 B（收到 1048771 B）
```

文件按扩展名自动分类（`.bin` → `其他/`），重名自动加 `(n)`（`probe.bin` → `probe(1).bin`）。

**端到端字节级闭环**（`tests/live-probe/e2e_verify.py`，**11/11 通过**）：
上传 4 MiB 已知文件 → 从手机 `/file/` 读回 → **sha256 完全一致**；
中文文件名原样保留且内容一致。接口回 200 不等于文件传对了 ——
中间有 multipart 分帧、流式解析、去重命名、落盘四道变换，任何一环错位都得到坏文件。

**吞吐上限说明**：纯解析（离线、直接执行交付的 .ets）可达 **132.8 MiB/s**，
所以解析器不是瓶颈；真机 15.63 MiB/s 的限制来自 WiFi 链路与
`fileIo.writeSync` 的同步写盘（同一文件换客户端测，数字在 10~16 MB/s 之间浮动）。

### 17.4 本次新增的验证工具

| 工具 | 作用 |
|---|---|
| `tests/upload-check/check.mjs` | 直接执行交付的 `.ets`：Content-Length 补全 + multipart 解析，**37/37 通过**。分片宽度覆盖 1/2/3/7/13/64/255/1024/4096/65536/256KiB/整包 —— 1 字节是最恶劣的情况，分隔符必被切开 |

### 17.5 顺带修的坑

- **`waitForData` 的定时器必须显式 clear**：旧实现数据先到时只 resolve 不 clearTimeout，
  每次「等数据」都在事件循环里留一个 15~60 秒的僵尸定时器。
  上传十几万次分片，就是堆十几万个待触发 timer。
- **chunked 请求体必须显式拒绝**（411 + 关连接）：`bodyLength()` 用 `-1` 表示它，
  旧代码 `if (bodyLen > 0)` 会直接跳过读取，未消费的 chunked body
  就被当成下一条请求的头部解析 —— 表现为莫名其妙的 400 或串包。
- **`FileSink.append` 加零拷贝快速路径**：切片出来的 `Uint8Array` 其 buffer
  通常就是精确大小，不必再复制一次。
- **上传响应正文是给人看的中文句子**，不是 JSON：网页拿到后直接
  `lightyear.notify(responseText, "success")` 显示，返回 JSON 用户会看到一串花括号。
- **`/chatUploadFile` 暂只落盘到本机**：它的原意是转发给 `address` 指定的设备，
  要走私有协议的 FS 发送流程（B1 批次）。当前在提示里**如实说明**转发未实现 ——
  假装成功但不转发，用户会以为对方收到了。

### 18.2 图标：为什么是重采样而不是矢量重绘

先做了精确测量（连通域 + 逐行扫描），确认原图是纯几何图形：

```

  #2 面积 75  x 41..63  y 66..70   笔记本底座
  #3/#5/#6                          WiFi 三弧 + 箭头
主色 #F24235（242,66,53），圆外透明
```

按测量结果**本来可以矢量重绘**（元素都是圆 / 圆角矩形 / 描边 / 弧），但 vivi 定调「直接用那张图片就行」，于是走重采样：

```python
big = im.resize((size*4, size*4), LANCZOS)
out = big.resize((size, size), LANCZOS)
out = out.filter(UnsharpMask(radius=1.2, percent=55, threshold=2))
```

- **两级 LANCZOS**：先放大 4 倍再收到目标尺寸，比一步 5.3 倍直放更干净。
- **锐化参数刻意保守**：`radius` 一大或 `percent` 一高，红白交界处会冒出白色光晕（halo）。1.2 / 55 是反复看了预览定下的。

### 18.3 状态栏重叠：沉浸式的代价

`EntryAbility` 里为了沉浸式开了：

```ts
win.setWindowLayoutFullScreen(true);
```

这行的含义是「内容铺到状态栏底下」，但**组件不会自动让位**。所以标题栏必须自己下移。做法是读系统的避让矩形：

```ts
const sys = win.getWindowAvoidArea(window.AvoidAreaType.TYPE_SYSTEM);
const nav = win.getWindowAvoidArea(window.AvoidAreaType.TYPE_NAVIGATION_INDICATOR);
this.topInset    = this.getUIContext().px2vp(sys.topRect.height);
this.bottomInset = this.getUIContext().px2vp(nav.bottomRect.height);
```

- **不写死数值**：刘海屏 / 挖孔屏状态栏高度不同，横屏还会变，写死一个 38vp 换个机型就错。
- 底部同理，`Tabs` 的导航条按 `bottomInset` 让位，否则会被系统手势条压住。
- 避让区是异步拿的（`getLastWindow` 返回 Promise），拿到后 `@State` 变更会触发重组，所以**首帧可能先画在状态栏下、下一帧才归位**。要彻底避免可以改在 `EntryAbility` 里取好再传参，当前实现选择了改动更小的方案。

### 18.4 两个编译坑

**① `tabIndex` 与组件基类属性重名**

```

Property 'tabIndex' in type 'Index' is not assignable to the same property
in base type 'CustomComponent'.
  Type 'number' is not assignable to type '(index: number) => CommonAttribute'.
```

`tabIndex` **是 `CustomComponent` 基类的既有成员**（类型是 `(index:number) => CommonAttribute`，用于焦点控制），自定义组件里拿它做「当前页签」会直接撞车。改名 `curTab`。

> 这类错误的报错信息不含文件名（只说 `in type 'Index'`），批量改名前先全局搜一遍组件状态变量名会更省事。

## 十九、文本消息三端互通 + 底栏配色（vivi 2026-09-30 第二轮决策）

诉求两条：

1. 加一个「消息」tab，手机与对端能**互相**发文字消息；
2. 底栏颜色统一 —— 系统小白条（导航条）那一条是灰的，上面 tab 栏是白的，两色拼接很扎眼。

### 19.1 消息链路：从「只收不发」补成三端互通

原先只有「网页 -> 手机」的收消息通道（`WebSocketSession` 把帧交给 `LanService.wsRelayChat`），
而 `wsRelayChat` 当时只写了日志，注释里挂着「跨设备转发待 B1 补齐 FS_MESSAGE 编码」。

这次把编码从 Java 源码里挖出来了，**没有猜**。

#### 协议字节序列（对照 `FileSend.sendMessage` + `LANService.broadcastMessage`）

```
[4B MAGIC_NUM 0x66677371]   未混淆                —— LanClient.connect() 已写
int      NEW_VERSION_4 = -2
string   deviceJson         发送方设备信息         —— FileSend.sendNewVersionFlag
int      FS_MESSAGE = 1105
boolean  isClip             让对端写入剪贴板
string   messageEnc         AES 密文的十六进制串
```

#### ⚠️ 第一个坑：消息密钥要「再解一层」

`FileSend.sendMessage` 是把**已经加密好**的 `message` 写出去的，真正的加密发生在
`LANService.broadcastMessage(Device,...)` 里：

```java
message = AESUtils.encrypt(msg, Config.MESSAGE_KEY);
```

而 `Config.MESSAGE_KEY` **不是**常量 `DEFAULT_MESSAGE_KEY` —— `Config.initPrefs()` 里还有一步：

```java
String messageKey = prefUtil.getString(PreConfig.MESSAGE_KEY, Config.DEFAULT_MESSAGE_KEY);
Config.MESSAGE_KEY = AESUtils.decrypt(messageKey, Config.KEY);   // ← 又解了一层
```

即：真正的密钥 = `AES-decrypt(DEFAULT_MESSAGE_KEY, KEY)`。
实测（node/OpenSSL 独立复算，48 字节密文 -> 32 字节明文 + 16 字节 0x10 padding）：

```
Ndsi3dklHn4ErC95z3u2QnxeAMQwkNJp      ← 32 字节，正好是合法 AES-256 密钥
```

漏掉这一层的表现是「两端各自都能加解密，但互相解不开」，非常像协议错位，实际差了一整层。

#### ⚠️ 第二个坑：`padKey` 的边界写成 `>=` 会误杀这把密钥

`AesCodec.padKey()` 原来是：

```ts
if (raw.length >= KEY_SIZE) throw new Error(...);   // ← 错
```

而 Java 的 `padKey` 只在 `keyLength < 32` 时才补 `'\0'`，**恰好 32 字节是合法的 AES-256 密钥**。
写成 `>=` 会把上面那 32 字符的密钥判成非法，表现为「消息发不出去 / 收到也解不开」。
已改成 `>`（见 `core/AesCodec.ets`）。

#### 三条通路

| 方向 | 落点 | 说明 |
|---|---|---|
| 手机 -> 局域网设备 | `service/TextMessenger.ets` | 新文件。建链 + 加密 + 写帧，一发一关（与原实现一致） |
| 网页 -> 局域网设备 | `LanService.wsRelayChat` | 解析浏览器 `cmd:1`，按 `selectedDevice` 定向或群发；`isClip` 透传 |
| 设备 -> 手机/网页 | `LanService.onMessageV4` / `onTextMessage` | 写入本机聊天列表，同时 `broadcastChatToWeb(isLeft=true)` |

约定（都对照原 Android 行为）：

- 网页发来的消息**不回显**给网页 —— 浏览器在 `sendMessage()` 里已经本地画过右侧气泡了
  （Android 侧传的也是 `shareWS=false`），回显会让同一条消息出现两遍。
- 手机端**主动**发消息时反而要推给网页（对应 Android 的 `shareWS=true`），
  这样「PC 网页 ←→ 手机 ←→ 安卓设备」三方能互相看见。
- `selectedDevice` 为空串 = 所有在线设备（与网页下拉框「所有设备」一致）。
  网页下拉框的 `value` 目前由 `wsDeviceListMessage()` 给的是纯 IP，
  转发时同时兼容 `ip` 与 `ip:port` 两种写法（Android 的 `address` 是后者）。
- 消息长度上限 700 字，与 Android `broadcastMessage` 里的判断一致。

#### 手机端自己发不出去时的兜底

没有在线设备时**仍允许发送**：消息会记进本机列表并推给网页端，toast 里如实说明
「当前没有在线设备，消息仅推送到网页端」。
不这么做的话用户会以为聊天功能坏了，而实际只是当前没有对端。

### 19.2 底栏小白条配色

原因很直白：`Tabs` 让位用的是 `padding({ bottom: bottomInset })`，
padding 区域露出的是**根节点的底色** `#F1F3F5`（灰），而 tab 栏本身是 `C_CARD`（白）——
于是导航条那一小条和 tab 栏颜色对不上。

改法：把 padding 换成一个显式的同色条。

```ts
Tabs(...)
  .barHeight(50)
  .barBackgroundColor(C_CARD)
  .layoutWeight(1)          // 去掉 bottom padding

// 底部安全区：高度取运行时拿到的导航条高度，颜色与 tab 栏一致
Row().width('100%').height(this.bottomInset).backgroundColor(C_CARD)
```

高度仍然来自 `AvoidAreaType.TYPE_NAVIGATION_INDICATOR`（本机实测 28vp），不写死。

### 19.3 消息 tab 的两个实现细节

**① 列表刷新要换引用**

`LanService` 里聊天记录是 `chatRing` 数组原地 `push/shift`，
但 UI 侧必须拿到**新数组**才会重渲染，所以 `onSnapshot` 里只在条数变化时做一次 `slice()`：

```ts
if (s.chat.length !== this.lastChatCount) {
  this.lastChatCount = s.chat.length;
  this.chat = s.chat.slice();
}
```

顺带把「只在条数真变了才 slice」当成节流 —— 传输进度会高频触发 `emit()`，
每帧都复制 200 条数组纯属浪费。

**② 气泡左右靠 Blank 顶开，不用百分比宽度**

气泡要贴着内容收缩（短消息不该占满一行），ArkUI 的 `constraintSize` 不支持百分比，
所以用「Row + 条件 Blank」把气泡推到左/右：

```ts
Row() {
  if (!m.incoming) { Blank() }
  Column() { ...气泡... }
  if (m.incoming) { Blank() }
}
```

### 19.4 验证

新增 `tests/text-message-check/check.mjs`（离线，不需要真机，**9/9 通过**）：

- 密钥派生结果 == 内置常量，且恰好 32 字节；
- 4 组载荷（英文 / 中文+emoji / 700 字 / 单字）写帧 -> 按接收端逻辑解回，字节全等；
- 密文是偶数长度纯 hex 且长度是 16 字节块整数倍；
- 负向用例：明文当密文喂进去必然抛错（证明"必须加密"这条不能省）。

> 写这个脚本时自己踩过一次坑并已修正：`decipher.update().toString('utf8') + final('utf8')`
> 会在分块边界把多字节 UTF-8 字符劈成两半，中文/emoji 解出替换字符 —— 是**脚本**的坑，
> 不是协议的坑（曾误报一次）。正确写法是先 `Buffer.concat` 再 `toString`。

## 二十、沙箱文件删除（vivi 2026-09-30 第三轮）

**现象**：收进来的文件全堆在应用沙箱里，界面只有「另存为」，**没有任何删除入口** ——
传错了、测试造的垃圾、重复接收的文件都无法清掉，空间只增不减。

### 20.1 界面落法

「接收到的文件」卡片两处新增：

| 位置 | 控件 | 行为 |
|---|---|---|
| 卡片右上角 | 「清空」 | 列表非空时才露出；删掉**全部**已接收文件 |
| 每一行 | 「删除」 | 删单个文件，位于「另存为」右侧 |

删除前一律弹确认框（`promptAction.showDialog`）。理由很实在：
沙箱里的文件在**系统「文件管理」里根本看不到**，删掉之后用户没有任何第二途径找回，
一步误触的代价远大于多一次确认。

### 20.2 ⚠️ 删除接口必须带路径守卫

`ExportService.deleteFile(root, path)` 只放行落盘根目录以内的路径，两条硬性判断：

```ts
if (path.indexOf('..') >= 0)  return '路径不合法，已拒绝';
if (!path.startsWith(`${root}/`)) return '该文件不在接收目录内，已拒绝删除';
```

**第二条的斜杠不能省。** 写成 `path.startsWith(root)` 时，
`${root}Backup/a.txt` 这种「同前缀的兄弟目录」会被判成在 root 之内而放行 ——
这就是一个现成的目录穿越口子。第一版我写成了 `startsWith(root)`，
自查时发现并已改成比到目录分隔符。

### 20.3 「清空」不能只清看得见的 40 条

`listReceived()` 有 40 条上限（避免目录大时卡 UI）。
如果「清空」直接遍历 UI 上的 `receivedFiles`，用户点完会发现空间没释放 ——
剩下的文件还在，观感就是"清空没生效"。

所以 `deleteAll()` 走独立的 `allPaths()` **全量扫描**（上限 3000 条保护），
确认框里显示的也是真实总数，不是列表里显示出来的条数。

删除后顺带 `pruneEmptyDirs()` 回收空目录；`rmdirSync` 对非空目录会失败，失败即忽略 ——
目录不空说明里面还有文件，本来就不该删。

### 20.4 验证

`tests/sandbox-delete-check/check.mjs`，离线 **17/17 通过**：

- 放行组：根目录子文件 / 分类子目录 / 嵌套目录 / 中文+emoji 文件名；

  root 目录本身、root 带尾斜杠时的兄弟目录；

| 候选 | 结论 |
|---|---|
| `photoAccessHelper.PhotoViewPicker`（系统相册 Picker） | **主选**。用户主动选，URI 带授权；不申请权限、不弹权限框 |
| 自己扫媒体库 + `getAssets` | 落选：要 `READ_IMAGEVIDEO` user_grant 权限，还得处理拒绝授权的流程 |
| 先复制到沙箱再发 | 落选：Picker 的 URI 可直接 `fileIo.openSync` 读，复制是白花一次 IO（几百 MB 视频尤其明显） |

**两个入口共用同一条发送链路**：差别只在选择器，拿到 uri 之后都走 `OutgoingFile.fromUri` → `service.sendFiles`。
所以新增的只是 `pickAlbumAndSend()`，发送逻辑抽成公共的 `sendUris()`，没有第二套实现。

UI 上是设备行**两个并列按钮**「相册」/「文件」，不叠进二级菜单 —— 选图是最常用的一种发送，多一次点击就多一次劝退。

**兜底**：`OutgoingFile.fromUri` 会 stat 一次拿大小，`sizeKnown=false` 就是打不开。
相册里偶尔会遇到（云端图没下载到本地、授权没生效），`sendUris` 里改成**跳过读不到的、能发的照发**，
而不是让 `FileTransfer` 遇到第一个就中止整批。

> ⚠️ **待真机验证（C 类结论）**：SDK `@ohos.file.photoAccessHelper.d.ts` 里 `PhotoViewPicker.select`
> 的注释写「photoUris … has permanent authorization and can be used **only by calling
> photoAccessHelper.getAssets**」，而我用 `fileIo.openSync(uri)` 直接读（这是绝大多数官方示例的做法）。
> 两者不一致，编译通过**不代表**运行时能读。若真机上出现「相册里的图读不到」，
> 报错码会打在日志里（`无法读取已跳过: <uri>`），届时再改走 `getAssets` + `PhotoAsset.open()` 读 fd。

### 22.2 文件页进度

`snapshot.transferText` 是服务层唯一的进度来源（`发送/接收 <文件名> <百分比>%（第 n/N 个）`），
共享页原来就有一条，文件页顶部再加一条同样的 —— 传完还要在这页「另存为」，看不见进度只能干等。

### 22.3 页签：共享 / 消息 / 文件

日志 tab 删除。日志仍要能拿到，所以在共享页底部留了一个「复制日志」按钮（复用原来的 `copyLogs()`），
不占版面，排障时还能贴出来。

索引全体平移：消息 → 1，文件 → 2。`onSnapshot` 的聊天自动滚动判断、`onChange` 的切页动作同步改。

> ⚠️ 这轮改的时候替换脚本漏删了旧 `onChange` 块的尾巴，留下一个孤儿 `try/catch`，
> 编译报 16 个错（`,' expected` / `Unexpected token`），位置全在文件末尾。
> 改这类 **if 块整体替换**时，务必确认旧块的收尾大括号一起被替换掉了。

## 二十三、本机 → 网页端的发送进度（vivi 2026-10-01）

**现象**：网页 → 手机有进度条（上一轮加的 `setOnUploadProgress`），
反过来**手机 → 网页没有**：手机上推文件给浏览器，浮层一片空白，只能看浏览器的下载条。

**根因**：字节出口不一样。

| 方向 | 走的路由 | 上一轮是否上报 |
|---|---|---|
| 网页 → 手机 | `POST /uploadFile`（multipart） | ✅ 已在循环里节流上报 |
| 手机 → 网页 | `POST /compressFiles`（打包） + `GET /downloadZipFile`（流式发字节） | ❌ 两处都没有出口 |

所以补的是**下载方向**的一对回调，与上传对称：

```ts
// HttpRouter
setOnDownloadProgress(cb: ((sent: number, total: number, name: string) => void) | null): void
setOnDownloadEnd(cb: ((ok: boolean, name: string, totalBytes: number, error: string) => void) | null): void
```

上报点只有两个，覆盖全部「本机发出字节」的场景：

1. `sendFileRange()` —— 流式发送循环里按 **200ms** 节流上报（8 MiB 一块，几毫秒就发完，
   不节流等于每帧重建页面），收尾再补一次 100%（最后一次节流之后那截不能丢）；
2. `compressFiles()` —— 打包阶段 `zlib.compressFiles` 不给回调，**没有可计量的总量**，
   用 `total = -1` + 整句文案（`正在打包 N 个文件…`）表示，UI 侧见到 `total < 0` 就原样显示、
   百分比给 0，别拿它去除以什么。

⚠️ 两个必须遵守的点：

- **结束回调成功失败都要发**。只发成功的话，浏览器中途取消下载时浮层会永远停在某个百分比，
  `onSnapshot` 里「transferText 非空 → 空」的跳变也不会发生，文件页的自动刷新跟着失效。
- **每块都让出主线程**（`DOWNLOAD_YIELD_EVERY = 1`）。块是 8 MiB，读块是同步 IO，
  不让出的话「发给网页」期间 App 按钮点不动 —— 和上传方向同一个病根。

LanService 侧复用同一对字段 `transferText` / `transferPercent`，不再给 UI 开第二条状态通道。

## 二十四、多台设备在线时「+」弹窗选设备（vivi 2026-10-01）

**诉求**：消息 tab 的「+」在多台设备在线时，先弹窗让用户选发给谁。

**为什么必须换掉 `bindMenu`**：菜单项（`bindMenu([...])`）是**静态**的，
只能在编译期列出「相册 / 文件」，做不到「运行时按在线设备数量决定要不要先问设备」。
原来的落法是选不到目标时 toast 一句「请先选目标设备」，用户根本不知道去哪选。

改成 `onClick → openPlus()`，用一个 `pickStep` 状态驱动两步弹窗：

| 情况 | 行为 |
|---|---|
| 已在上方胶囊选了具体设备 | 直接进第 2 步（相册/文件） |
| 只有一台在线 | 直接进第 2 步（目标就是它） |
| 多台在线且选的是「所有设备」 | 先弹设备列表（第 1 步） |
| 没有在线设备 | 提示，不弹 |

选完设备顺手把 `chatTargetIp` 同步过去，上方胶囊跟着变 —— 下一次按「+」就少一步。

**UI 上的两个坑**

1. 遮罩和卡片必须是 **Stack 的兄弟节点**：遮罩自己吃点击用来关闭，
   卡片也挂一个**空 `onClick`** 把点击吃掉 —— 否则点卡片会穿透到遮罩，弹窗直接被关掉。
2. 两步表单不要用 `CustomDialogController`：跨步骤传状态很别扭，
   一个 `@State pickStep` 切换内容就够了（浮层照样是应用内的，不是系统级窗口）。

文件发送仍是**单连接模型**，不支持群发，所以第 1 步不提供「所有设备」选项，
弹窗里也写明了这一点，避免用户困惑。
